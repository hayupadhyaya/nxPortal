# Host

Mac-side pieces in `PortalKit/Sources/PortalHostCore/` (macOS only).

#### tap-server

- `TapServer` (actor, thin) over `TapCore`: POSIX `AF_UNIX` stream socket, accept and read on one serial queue, writes on a second.
- Path: `HostDefaults.socketPath(instance:)` = `<HostDefaults.socketDirectory()>/tap-<pid>-<instance>.sock`; the folder is `nxportal` inside the user's own temporary folder (`confstr(_CS_DARWIN_USER_TEMP_DIR)`), socket 0600, path at most 103 bytes (else `TapServerError.pathTooLong`), backlog 1. `HostService` takes a process-wide instance number (a counter), so two services in one process never share a path; `HostConfig.tapSocketPath` overrides it.
- `TapServer(socketPath:requirePrivateFolder:)` (`HostService` sets it only when `tapSocketPath` is nil): the folder is made 0700 when missing; it must be a directory (not a link) of this user with mode 0700, else `start()` throws `.unsafeFolder` and creates nothing. `start()` removes `tap-<pid>-<n>.sock` sockets of this user whose pid is not running (`kill(pid, 0)` says `ESRCH`; a pid that exists, ours included, stays). An explicit path without the flag keeps the old behaviour (tests under the system temporary folder). A `start()` that fails after `bind` removes its socket file.
- One game at a time: no `accept` until the current connection has closed.
- First message must be `hello`, within 5 s of accept (else closed, `.closed`); wrong version -> `.refused("tap protocol <theirs>, Host speaks <ours>")`; other first message -> `.refused("expected hello")`.
- Tap protocol 2 only (`ProtocolVersion.tap`): a tap-1 game is refused with the version message.
- After hello: `video` (with its mark and token), `audio` (2 channels only, else `.refused("audio must be stereo")`), `prepare`. A message of an unknown type is skipped by its length (`.skipped(type:)`, the connection goes on); any other known message, a malformed known message, a framing error or an oversize length closes.
- `.closed` exactly once per connection. `events`: one consumer, unbounded, finishes on `stop()`.
- `send` before hello or with no game: dropped. Write error closes.
- `stop()` wakes the loops through a pipe, closes everything, removes the socket file. `start()` after `stop()` throws `.stopped`.
- `send` is `nonisolated` (callers keep their order, no suspension).
- `disconnect()` (`nonisolated`): shuts down the current connection (its game reads EOF); accepting goes on.
- Every descriptor (listener, accepted socket, wake pipe) is `FD_CLOEXEC`: a launched game inherits none.

#### game-launch

- `GameLaunching` / `RunningGame` protocols; `AppLauncher(apps:logDirectory:)` runs `<app>/Contents/MacOS/nxnative`.
- Environment: the Host's, plus `HostService.launchEnvironment(file:choices:)` (per game; `launch(titleID:socketPath:environment:)`, a launcher without the third form ignores it): `HostConfig.gameEnvironment(titleID)` first, the per-game choices over it for the same variable (`§ options`), plus `DM_STREAM=<socket>`, `DM_LAUNCHER=0`: those two are the Host's own and win (the merge drops them from both inputs, `AppLauncher` sets them last).
- `LaunchError.notFound` (no app for the title), `.notRunnable` (binary missing or not executable).
- `logDirectory`: stdout and stderr appended to `<dir>/<titleID>.log`; nil inherits.
- `terminate()`: SIGTERM, then after the grace (`RunningProcess(killGrace:)`, default 5 s) SIGKILL to the launcher's children (`proc_listchildpids`) first, then the launcher; returns once the game has exited (so `HostService.stop()` and a Host that quits right after it leave no game running, even one that ignores SIGTERM), or 3 s after the SIGKILL (`exitCap`) when it still has not (uninterruptible I/O): then `AppLauncher`'s `report` gets `<titleID>: did not exit after SIGKILL` (no path; the app logs it as a `note`). Safe twice and after exit. `waitForExit()`: status, or 128 + signal.
  - Why children: `Contents/MacOS/nxnative` is a launcher that runs the game as a child and forwards only SIGTERM; SIGKILL cannot be forwarded.
- Start timeout: `HostConfig.startTimeout`, default 600 s; state stays `starting` meanwhile. `portal-hostd` has no option for it.
- Known limit: macOS scans a new or changed game bundle before its first instruction (minutes for a large game); later launches skip it. Plan B's Host app should start a changed game once ahead of time ("preparing").

#### test-support

- `PortalTestSupport` (depends on `PortalHostCore` for the launcher protocols): `FakeGame`, `FakeLauncher`; `portal-fakegame --socket <path> [--prepare-hold <s>]` (the latter: reports 360 of 1000 and shows no picture for that long, for menu shots) wraps `FakeGame`.
- `FakeLauncher(connectDelay:)`: seconds between launch and the game connecting (default 0).
- `FakeGame` speaks tap protocol 2 as the tap does it (`tap.md § ltr`): the encoder has real long-term references (`EnableLTR`, tokens from `RequireLTRAcknowledgementToken`, `AcknowledgedLTRTokens`, `ForceLTRRefresh`), wire tokens carry the epoch (`epoch << 24`, +1 per encoder session), `ltrAck` keeps a token only of this epoch, issued since the last key frame and not pending; `refresh` is a repair frame (flags 2) when an acknowledgement reached the encoder since the last key frame, else a key frame; a refresh while one is due or in the encoder is served by it; a refresh answered with a key frame although a repair frame was asked for is counted (`repairsAnsweredWithKey`) and followed by a key frame. `FakeGame(repairDelay:)` (default 1): ordinary frames sent after a `refresh` before its repair frame (frames in flight that still depend on the lost frame). `longTermReferences: false`: as a tap whose encoder refused them (tokens -1, refresh = key frame). `preparePhases: [total]`: `prepare` start, half way and done per phase before the first frame; `prepareSteps: [PrepareStep]` sends explicit `prepare` values instead; `stall` (s) spreads them over that time before the first frame (`FakeLauncher(stall: 3)` with no phases or steps: phase 1 at 100, 600, 1000 of 1000). `sentFrames`: mark, token and size of the newest 600 frames.
- `FakeGame` sends nothing before `config`; HEVC via VideoToolbox (low-latency, no reordering, keyframes only first/on request/on size change/for a refresh with nothing acknowledged); size = game size fitted to the config cap, even, never up; rate = min(fps, maxFps). Like the tap: sound continues while paused (no video); a `config` of the same size makes no key frame (the encoder is made again only on a size change).
- Video data = length-prefixed NAL units; key frames start with VPS, SPS, PPS. `captureNs` taken before encoding.
- Sound: 440 Hz, 240-frame stereo blocks, absolute-deadline pacing.
- `FakeGame(paddedToBitrate:load:)` pads frames to the configured bitrate (a repair frame as an ordinary one, a key frame 4 x) (`load`: a quiet start, or sizes that double every other second); `FakeLauncher(fps:paddedToBitrate:load:)`; `framesSent` -> `portalkit.md § test-network`. `HostConfig.tapSocketPath` gives each in-process Host its own tap socket.
- `sentVideo` keeps the last 600 frames; `received` everything the Host sent; `isFinished` once `run()` returns.
- Tests use `/tmp/nxp-t-<hex>.sock` and await events with a 10 s limit; the one fixed wait is the "second game waits" negative.

#### library

- `GameLibrary(roots:).scan()`: `root/*.app` and `root/*/*.app` whose `Contents/Info.plist` has `DMTitleID`.
- A root that is missing or unreadable contributes nothing (no error); the other roots are listed.
- One entry per title: the first copy that can stream (`DMStream`), else the first found, in the roots' order. A launch names a title, so an ordinary install in an application folder must not hide the streaming build in another folder.
- `HostService` scans off the actor (a detached task; media, tap events and the tick go on) when a `listRequest` or `launch` arrives, and reuses the result for 2 s (`scanLifetimeNs`); the reply waits for the scan, nothing else does. `library` is a `var` and `lifecycle.scannedAt = nil` drops the cache (`setLibraryRoots` does both and bumps `lifecycle.libraryEpoch`, so a scan that began earlier is not kept). `ScanScenarioTests`: 6,000 app folders and a list request mid-stream, longest frame gap under 100 ms (at 2,000 folders on a warm cache the on-actor scan cost 60-80 ms: too close to tell the cases apart).
- Name: `CFBundleDisplayName`, else `CFBundleName`, else the file name. `streamable` = `DMStream` is true. Sorted by name; unreadable bundles skipped.
- Icons (`GameArtwork`, `HostService+Art.swift`): `Contents/Resources/<CFBundleIconFile>` (`.icns` added when it has no extension; a file over 64 MB is not read); its largest representation decoded as a thumbnail at 512 (never the full bitmap), PNG; over 512 KiB -> 256, then 128, else none. `hash` = SHA-256 hex.
  - Kept once, in the service: `artwork[titleID]` (icon URL, its modification date, hash, PNG). Each `listRequest` checks every listed game's icon date off the actor and rebuilds only a new or changed file; games no longer listed are forgotten. `artwork(titleID:)` (`HostService+Admin.swift`) is the one read for the menu; there is no second copy.
  - `artRequest` (admitted sessions only): a title ID over 64 bytes of UTF-8 or a hash not exactly 64 bytes of UTF-8 (a hash is 64 ASCII hex characters) is dropped (no queue entry, no reply: nothing a device sends is echoed back); else queued on its link (at most 128; more are dropped), served in order by one worker per link. Unknown title or hash: `art` with `count` 0 (a dictionary lookup). Known: its chunks in order, each sent only after the connection has taken the previous one (`contentProcessed`), so a device that does not read holds the Host to one chunk in flight (test: a device that stops reading). At most 4 transfers at once over all links (`maxArtTransfers`; a slot is handed to the next waiter).
  - The icons are the game publisher's material: never logged, never in the repository or a fixture (tests draw theirs with `FakeArt`, `PortalTestSupport`).

#### pairing-store

- `PairingStore(secrets:)` (when `HostConfig.secrets` is set; `storeURL` is then never read or written): identity raw key under `host.identity`, peers as JSON under `host.peers`; created on first use.
  - `init(secrets:)` is serialised by a process-wide lock (a first run's read-then-create never interleaves; 20 concurrent inits give one identity). A new identity is written and read back, and the stored value is used. Across processes the store has no write-if-absent: the Keychain store updates, then adds, so a duplicate add throws `errSecDuplicateItem`; the init then re-reads and uses what is stored. The file store (`FileSecrets`) is last writer wins, and the read-back converges on its final value.
  - A `host.identity` that cannot be read throws and is never replaced (a new one would orphan every pairing); the file-backed store throws too. A `host.peers` that cannot be decoded counts as no paired devices (one log line, no bytes); the file-backed store, being one document, throws instead.
- `PairingStore(fileURL:)`: JSON `{ "identity": <base64 private key>, "peers": [PairedPeer] }`; identity created on first use.
- Written atomically (0600 temp file, renamed); parent directory created 0700. Lock-guarded.
- `PairedPeer { key, name, alias?, kind?, added? }`: `name` is the device's own (from `pairStart`, then each `hello`), `alias` the Host's rename (menu only), `kind` from `hello`, `added` the pairing date (wall time: `PairingStore.wallClock`, the one stored date). A file without the three optional keys loads as before; a value of another type reads as nil.
- `add` of a known key keeps its place, `added` and `alias` (a re-pair renumbers nothing); a new key gets `added = now`. `update(key:name:kind:)` (from a `hello`, once its device has proved its key) replaces `name` / `kind`, never `alias`; `setAlias(_:key:)` sets or (nil, or a name that cleans to nothing) removes it. Every name the store keeps goes through `DeviceName.clean` (40 characters / 120 bytes, no control or format characters) whoever sends it; a name that cleans to nothing changes nothing (a new pairing is "Device").
- Never logged. Known limit: the key sits in a file; the app moves it to a secret store (`HostConfig.secrets`).

#### service

`HostService` (actor) -> `HostService.swift` (control), `HostService+Media.swift` (media, tap, tick, games), `ControlListener.swift` (TCP), `MediaSocket.swift` (UDP), `MediaSender.swift` (paced sending -> `§ sender`).

- Inbound events reach the actor through ordered streams, one long-lived task each: control, datagrams, tap events, a 100 ms tick; one exit waiter per game. No task per packet.
- Control: `NWListener` TCP on `config.port` (0 = any); Bonjour `_nxportal._tcp` named `config.name` only when `advertise`, TXT `id=<discoveryID>` (`§ admin`).
- Media: two POSIX UDP sockets for the service's lifetime, one IPv4 and one IPv6-only, on the same ephemeral port = `Welcome.udpPort` (the IPv6 one binds first; a port taken for IPv4 is tried again, up to 16 times); 4 MiB buffers; a datagram over 1,200 bytes is dropped unopened. Sessions told apart by session ID.
- Answers leave from the address the device sent to: packet info in (`IP_RECVPKTINFO`, `IPV6_RECVPKTINFO`) gives each datagram's arrival address (`UDPAddress.local`), packet info out (`IP_PKTINFO` source, `IPV6_PKTINFO` with the arrival interface for a link-local address, else interface 0) sets it on every answer (`sendmsg`, the control message built in place: no allocation per datagram). The address follows the newest datagram that opened, so the source does too. Why: a device's media link is a connected UDP flow and drops anything from another address of the Mac; on a Mac with several addresses (two interfaces in one subnet, or a temporary IPv6 address) the kernel's own choice is the default route's. Two sockets because macOS ignores an IPv4-mapped source given to a dual-stack socket (verified: the answer left from the default address). `MediaSocketSourceTests` send from one local address to another (IPv4: a non-loopback address to 127.0.0.1; IPv6: `fe80::1%lo0` to `::1`, as `::1` may not answer a non-loopback address at all).
- Unadmitted connections: at most 16 (`maxUnadmitted`; a new one above is cancelled at once); an unadmitted link is closed `HostConfig.unadmittedTimeout` (10 s) after its last valid step (open, `pairStart`, pairing `.ok`, `hello` accepted; tests shorten it). The one owning the active pairing lives until the pairing ends.
- A connection opened around `stop()` is cancelled (listener after its stream finished; the control task drains the finished stream instead of being cancelled).
- Failure: `HostStatus.failed(text)` (text for people, no address, no path) means the service is not serving; nothing replaces it. Two causes: a `start()` that threw, and a control listener that failed after it was ready (`ControlEvent.failed`; test hook `ControlListener.failForTest(_:)`). The second leaves the connections as they are and accepts nothing new; the app calls `stop()`.
- Clock: `HostConfig.clock` (default `HostConfig.monotonicNow`: uptime mapped onto `Date`, so a wall-clock step changes nothing) feeds every session timer through `HostService.now()`: the model's silence and 500 ms rules, unadmitted links, game start and quit grace, session length and first-datagram time in the session-end line. Pairing expiry stays on wall time (a person sees it, and the code's lifetime is a security window), and so does the date a pairing is stored with; those four lines carry `// wall time:`. `ClockSweepTests` fails when `Date()` appears in `PortalHostCore` anywhere else.
- Teardown: `HostService+Lifecycle.swift` `shutdown()` is the one teardown (tasks cancelled, control, sender, media, tap, game, `status` and `sessionEnds` finished). `stop()` runs it; a `start()` that throws reports `.failed` and runs it, then rethrows: nothing it opened is left (both UDP sockets, the tap socket and its file), and the object is used up (a new `HostService` starts again). `stop()` called twice (or during `start()`): every call returns only when the one teardown has finished (a `Task` in `lifecycle.teardown`); a `stop()` during `start()` makes `start()` throw `CancellationError` at its next check (before the media socket, before the listener, after the listener) and nothing opens after it. `ControlListener.stop()` is remembered: a `start()` after it (or one that was past its first await when it ran) throws `CancellationError` before the listener opens, and the guard after `control.start` calls `control.stop()` again, so the TCP port and the Bonjour service are never left bound. Teardown awaits `ControlListener.stopAndWait()` (the listener's own `.cancelled`, 2 s at most): when `stop()` returns the pinned port is free, so a restart on the same port binds at once (`ControlListenerRestartTests`, 20 rounds). Test hooks `holdStart` / `holdScan` / `ControlListener.holdBeforeStore` hold those awaits.
- Frames: `ControlFramer`; JSON in the clear before `welcome`, `StreamSealer` with the control keys after. A frame that does not open or decode closes the connection.

| Phase | Accepts | Else |
|---|---|---|
| clear | `pairStart` -> `pairChallenge`; `pairProof` -> `pairResult`; `hello` | close |
| welcomed | sealed `ready` -> admit | close |
| admitted | `listRequest`, `launch`, `resume`, `quitGame`, `bye`, `artRequest`, `liveSettings`, `optionsRequest`, `setOption`, `resetOptions` | ignored |

- Pairing: `beginPairing()` = new `PairingHost` + code, status `.pairing`; replaces any earlier one. `pairStart` with none -> `.expired`. Second `pairStart` replaces the exchange. `.ok` stores the peer; `.ok` / `.locked` / `.expired` / 120 s end pairing.
- `hello`: version -> `refuse(.version(host:))`; unknown key -> `.unpaired`; what the hello claims (its `name`, cleaned again, and its `kind`) is kept on the link and stored (`PairingStore.update`) only in `admit`, AFTER the device proved its key (its sealed `ready` opened) and before the model admits: the hello is unsealed and carries a public key, so until then nothing it says is written, shown or published (a store that cannot write keeps the old ones and the session goes on). A hello alone can still learn a playing device's shown name from a `busy` refusal if it knows a paired key (todo.md); another device live AND playing (`model.playing`) -> `.busy(device:)`; refusal then close. Another device live in a library session (not playing): the newcomer goes on; at its admission the library session gives way (the model treats it as left, then admits the newcomer), is sent a sealed `bye(takenBy: <newcomer's shown name>)` and closed, its session-end line `replaced`. Else fresh ephemeral, `SessionKeys.derive(role: .host)`, random non-zero session ID, `welcome` in the clear.
- Render size: the first tap `video` frame (even with no playing session) and every change set `Game.render` (`RenderSize.fitted`: width, height, `exact` only when the fitted picture is under the hello's cap on BOTH sides; the tap fits by aspect and never scales up, so a side at the cap, within 2 for the even rounding, is a lower bound (the app keeps every size up to the first one larger than it on both sides offered; a bound only grows, an exact size replaces any bound it is not strictly below); a game exactly the cap's size cannot be told from a scaled one) and send `gameState`; every `gameState` of the running game carries it; a new `Game` has none until its first frame. `FakeLauncher(width:height:)` is the fake game's picture size.
- Library session: a `hello` with `resume: false` is admitted with `model.admit(resume: false)`: the game is never resumed for it (a playing session of the same device it replaces stops, the game pauses); it is told `gameState` as it is (`paused`, or `running` + `preparing` while a pause is owed) and gets no video or sound while `model.playing` is false. `resume` -> `play()`: the model resumes a paused game (an owed pause is just cleared, no `pause(false)`), and a session that only now plays is sent the state and a `keyframe` even with nothing to resume. `launch` of the starting or preparing (not paused) game's title from a session not playing is the same as `resume`; any other `launch` with a game present is `"<name> is running"`; a launch that starts a game marks the session playing first (`launchRequested`), so the game is not paused under it at its tap `hello`; a launch that throws calls `model.launchFailed` (not playing). A resuming `hello` with no game on the Host is a library session (`admit(gameExists: game != nil)`).
- Start rate: a `hello` with `startBps` keeps it, clamped as a `rate` (`[1 Mbit/s, ceiling(of:)]`), as the session's `rateBps` from `welcome`; every `config` for the session (admission, the game's tap `hello`) carries it until the first `rate` replaces it (the same value: a repeat). No key: `rateBps` nil until the first `rate` (the ceiling until then, as before). A `rate` datagram of a session not admitted yet changes nothing (the client sends its first `rate` only after the Host's first sealed frame, which follows admission).
- Admission at the first sealed frame (`ready`), never at `hello` (public keys travel in the clear). Before it: no model call, no game change, no media. A welcomed session's datagram that opens records its address only.
- Admit busy (race: the live session started to play after the newcomer's `hello`) -> sealed `bye`, close. Same device again -> the old connection is closed and dropped (no `takenBy`).
- `input`, `keyRequest` and `repair` from a session that does not play are dropped (a packet for the silence rule only): a library session moves no pad of a game paused or starting under it.
- `resume` with no game (a stale tile) plays nothing: the session is told the idle state and stays a library session (`play()` and `HostSessionModel.resumeRequested(gameExists:)`).
- After admit: the model's actions, `gameState` (current), `config` (client's size clamped to at least `HostDefaults.minWidth` x `minHeight` (320 x 180) and rounded down to even, `min(maxFps, 60)`, bitrate = the session's newest `rate` if one came (else its hello's `startBps`), else `min(hello.bitrate ?? HostDefaults.bitrate, HostConfig.maxBitrate)`, never under `HostDefaults.minBitrate` (1 Mbit/s)) + `players(mask: 1)` if a game is connected and the session plays (`model.playing`; a library session never reconfigures the game: size, frame rate and rate stay the last playing session's (`playerHello`, set whenever a playing session configures the game, the game's tap `hello` included) until a session plays: `resume`, or `launch` of the starting game, sends the `config` with its values before the game resumes; an admission that plays does the same, its `config` going out before the model's `resume` and `keyframe`, in that order); a picture's size (`render`) is judged against the playing session's limit, else `playerHello`'s, never a library device's; the 250 ms between rate configs starts afresh, so the new session's first `rate` goes to the game at once.
- `liveSettings` (control, admitted session only; before admission it ends the connection; a ceiling under the game's current rate reaches the encoder at once as a `config`, with no wait for the client's `rate`: the Host is the authority, and the client's own controller is already under the same ceiling, so its `rate` asks for the same value or less): `ceilingBps` (0 ignored) is clamped to `[1 Mbit/s, maxBitrate]` and kept as `Session.ceilingBps`; from then on it replaces the hello's wish as the ceiling (`ceiling(of:)`: the clamp of every `rate` and the bitrate of the next tap `config`, so a game starting after the message gets it); a `rate` still queued for the 250 ms interval above the new ceiling is cut to it too (never sent above it); a stored rate above it is cut to it (no `config` is sent for that: the device's own lowered `rate` datagram does); a session that does not play changes only what it keeps, never the game. `panel` is kept as `Session.panel` (the level the Host's sampler will read). Both live and die with the session; `HostService.liveSettings()` (public) returns them (nil with no live session), for tests and the app. A running game's process is never touched.
- Default bitrate: `HostConfig.defaultBitrate` (default `HostDefaults.bitrate`, 20 Mbit/s) stands for a hello with no `bitrate`; `maxBitrate` caps it as it caps a wish.
- Rate: a `rate` from the live session is clamped to `[1 Mbit/s, max(min(live ceiling ?? hello.bitrate ?? default, maxBitrate), 1 Mbit/s)]` (the wish stays the ceiling until a `liveSettings` replaces it) and kept on the session (`Session.rateBps`). With a game connected and the session playing it goes to the tap as a `config` (a session that does not play keeps it for when it plays) with the same size and frame rate and the new bitrate (`sendConfig`: the resend budget, `videoBitrate` for `hostStats.rateBps` and the sender's pacing rate follow), at most one per 250 ms (`rateIntervalNs`): one pending slot (`pendingRate`), the newest replaces it (a rate equal to the applied one clears it), so a cut never waits behind an older increase; it is applied by the first datagram from the live session once 250 ms have passed since the last config (input comes every 8 ms) or by the 100 ms tick, and at once, before the `keyframe`, when a `keyRequest` passes its limit (the key frame is sized by the newest rate). A `rate` sealed for a session that is not the live one changes nothing (as every datagram: its address only).
- Only the live connection reaches `clientLeft` (close, `bye`, failed frame). A silence detach (model tick) closes the live connection. Every end of a live session also gives one session-end line (`§ session-end`).
- Packets for the silence rule: sealed control frames and opened datagrams. The limit is 10 s (`HostConfig.silenceTimeout`, default `HostSessionModel.defaultSilenceTimeout`; tests shorten it): a client that stalls for up to 9 s stays live (pads neutral after 0.5 s without input, once), at 10 s `clientLeft` pauses the game.
- While the client is unreachable (a stall): the game keeps producing; the sender has nothing to wait for (a UDP `sendto` to an address that does not answer succeeds), so frames leave into the void and nothing is queued. If the socket refuses (`.wouldBlock`), the backlog rule keeps at most about 100 ms of video waiting (older unsent frames dropped whole, never a key or repair frame) and the urgent queue (sound, pongs, `hostStats`) keeps the newest 256 datagrams, so 9 s of refusal leaves 100 ms of video and about a second of sound, not 9 s. The resend store (0.5 s of fragments) and `keyRequest` limit (one per 100 ms) do not depend on the silence limit; a `nack` after the stall for a frame older than 0.5 s finds nothing. After the stall the client restarts its stream and asks once for a key frame (`client.md § session`): it gets the current picture, not queued ones.
- Media socket: `SO_SNDBUF` / `SO_RCVBUF` 4 MiB, non-blocking `sendto`; `transmit` returns `.sent`, `.wouldBlock` (`EAGAIN` / `ENOBUFS`: the sender keeps the datagram and tries at the next slice) or `.failed` (any other error: counted by `MediaDropCounter`; once a second while there are any, one log line `media: <n> datagrams not sent (send failed)`, `Logger`, subsystem `nxportal`, category `media`).
- Traffic class: the media socket sets `SO_NET_SERVICE_TYPE` = `NET_SERVICE_TYPE_VI` (interactive video, the class the client's `.interactiveVideo` maps to; the other video-like values are `AV` streaming and `RV` responsive, which tolerate delay); a failed `setsockopt` is logged once (`media: could not set the traffic class`) and ignored.
- Size limits for high bitrates: tap message 8 MiB (`TapFramer`), client `FrameAssembler` 8 MiB per frame (7,314 fragments), fragment count UInt16 (65,535, 75 MB); at 200 Mbit/s and 60 fps the average frame is about 0.4 MB and a key frame a few MB, so there is about 2x headroom; the 5 MiB frame split / assemble test covers the path. A frame over 8 MiB closes the tap connection (`tooLarge`).
- Tap `video` and `audio` are dropped while `model.gamePaused` (the tap keeps sending sound while paused) and while the live session is not `model.playing` (a library session).

| In (datagram) | Effect |
|---|---|
| does not open | dropped; address and timers unchanged |
| `input` | player 0, `seq` newer than last accepted -> `pad` (+ `motion`); else dropped |
| `keyRequest` | `keyframe`, at most one per 100 ms (a pending `rate` goes first) |
| `repair` | `refresh`, at most one per 20 ms (a pending `rate` goes first); the game decides repair frame or key frame -> `§ ltr` |
| `ack` | `ltrAck([token])` for that frame's token, when it has one and is newer than the last acknowledged -> `§ ltr` |
| `rate` | clamped, then a `config` now or once 250 ms have passed since the last (newest wins) -> Rate above |
| `ping` | `pong(clientNs, CLOCK_UPTIME_RAW)` |
| `nack` | the named fragments from `ResendStore`, each sealed afresh (a new counter) and queued ahead of the next frame's slice, 32 a slice |

- Resend store (`ResendStore`, a value type, time from the caller): every video fragment as it goes out, unsealed (the client refuses a replayed counter), for 0.5 s, at most 64 MB (oldest frames first); a fragment whose slot is filled, or whose count differs, starts that frame number afresh. A `nack` resends at most 512 fragments, within a per-session budget (a token bucket in payload bytes: refills at the video bitrate the tap was told, `setBitrate` from every `config` (the session's rate), 0.2 s of it deep; full again on `clear`); the same fragment at most once per 4 ms; an unknown frame (never sent, older than 0.5 s, from a stopped game) or an index at or past the frame's count resends nothing. Refusals are counted (`ResendStore.Refused`: unknown frame, bad index, too soon, over the limit, over the budget; `HostService.resendRefused`), never logged per datagram; the Host has no stats line yet. Cleared when a game starts (tap `hello`), pauses, exits or is abandoned, when a session is admitted and when the live session ends.
- Out: tap video -> `FrameSplitter` (the tap's mark, key or repair, copied into every fragment) -> kept in the resend store, one sealed datagram per fragment; tap audio -> one `audio` datagram, per-session `seq` from 0. Only to the live session, only once its address is known (source of the newest datagram that opened).

| `requestKeyframe` | `keyframe` (not rate-limited) |

- Games: list = library scan (cached 2 s, `§ library`) + `config.extraGames`; the running game carries its state.
- `launch` order: a game present -> current state + `"<name> is running"`; unknown -> `(.idle, "not found")`; not streamable -> `"rebuild needed"`; else (after the library scan, `§ library`; a `stop()` during the scan ends it with no launch) `.starting`, `launcher.launch(socketPath: tapSocketPath)`, throw -> `"launch failed"`.
- Tap `hello` -> `gameStarted`, `config` + `players`, `gameState`. A tap `hello` with no game launched -> `quit`. No `hello` within `HostConfig.startTimeout` (default 600 s) of a live process -> terminate, `"did not start"`; a process that exits first is reported at once. `.refused(text)` -> terminate, `(.idle, text)`.
- Exit (`waitForExit()`) -> `gameExited`, `(.idle, "exited (<code>)")`; Host stays up. `quitGame` -> `quit`; still running 5 s later -> `terminate()`.
- `gameExited` and every abandon -> `tap.disconnect()`: a leftover process still connected gets EOF, the next game is accepted.
- Tap closed while the game is connected -> the quit grace starts (as for `quitGame`); still running 5 s later -> `terminate()`. `terminating` is set only once there is a handle.
- Tap `prepare` (the game prepares before its first frame; the tap sends no video or sound until the last one): the newest is kept per running game (`gamePrepare`), one `notes` line when a phase starts (`game prepare: phase <p> started (<done>/<total>)`) and one when it ends (`game prepare: phase <p> done (<total>/<total>) in <s> s`), none per message; forwarded to the device as `GameState.preparing` (next bullet). Nothing on the Host times a game out for being alive without a frame: `startTimeout` ends at the tap `hello`, which comes before the preparation; the session's silence rules run on the client's datagrams, not on video.
- Preparing (`PreparingTracker`, `GameState.preparing`; time is an argument, uptime ns): preparing from launch until the first picture, and again while the game is alive, not paused and its newest picture is over 2 s old (games that send no `prepare`); never for a paused game. The state carries the newest `prepare` while it is under 5 s old and has a total; else `Preparing.waiting` ("waiting for the game"). `done` is clamped to a non-zero `total` and never lowers within a phase; a new phase number starts afresh. Sent to the live device on a change: entering and leaving at once, a progress change at most every 500 ms (`preparingIntervalNs`, from `tick` and each `prepare`); every `gameState` (a new session's first included) carries the current value. Pictures feed the tracker before the "paused / no address" drop.
  - A session that ends while the game is preparing does not pause it: `perform(.pauseGame)` sets `Game.pauseDeferred` instead of sending `pause(true)` (the model still counts the game as paused for its own rules; `gameState` says `running` until the pause is sent). The pause goes out once, when the tracker leaves preparing (the first picture, fed even with no session), unless a playing session is live: a library session of any device does not stop it (it is then told `paused`); a session that plays meanwhile (the same device resuming on admission, or any session's `resume` / `launch` of the game) clears it (no `pause(false)` for a game never paused) and is never paused under. `tap hello` with no playing session defers the same way. The game ending meanwhile takes the flag with it (`Game.pauseDeferred`). Session-end reasons and "a game alive without a frame is never ended" are unchanged.
- Tap message of an unknown type: counted per type (`skippedTap`), one `notes` line for the first of each type.
- `notes`: an `AsyncStream<String>` of those lines (also to the unified log); `portal-hostd` prints them.
- Status yields on change: pairing(code, until) > live(device, game name) > paused(game, no device) > idle. `until` = the pairing's start + `PairingLimits.lifetime` on the wall clock, for display only (the expiry is decided in `tick`).
- `stop()`: the live session's end line (`host-stop`), tasks cancelled (control task drains), listener + connections + UDP closed, tap server stopped, game terminated, power released if held, `status` and `sessionEnds` finish.

#### load

- What: the Mac's load for the numbers panel at "full" (`load` datagram 0x2B, `portalkit.md § wire-network`). Numbers only: no process names, paths or addresses. Not sent: temperatures, watts, frequencies, battery.
- When: `HostService.serviceLoad` (100 ms tick) samples only while the live session is playing and its `liveSettings.panel` is `full`. Anything else (`off` / `fps` / `compact`, no session, a paused game, the session ended) calls `stopLoad()`: the sampler is dropped, the frame clock emptied, a reading still in flight is discarded (`loadGeneration`). Cost below "full": one comparison per tick, one `if` per video frame.
- Cadence: a sampler (`HostConfig.loadSampler()`, one per stretch at full) takes a baseline read when the stretch begins (CPU shares need two readings), the first datagram follows 0.5 s later, then one a second. A slow read is skipped, not queued (`loadInFlight`).
- Off the media path: the read runs in `LoadRunner`, an actor of its own, awaited from a `Task`; the service's actor (video, control, tick) never waits for it (`testASlowReadNeverDelaysVideo`: a 1.5 s read, video keeps flowing). The datagram goes to the sender's lazy slot: behind every video and resend datagram, never on the urgent queue; lost ones are not resent.
- Frame fields: `FrameClock` (per-frame `captureNs` of the tap's video frames, the game's clock) -> fps, mean, p95 (nearest rank) and max of the gaps since the last reading; bounded (1,024 gaps); nil with no gap (fields 0). The last frame is kept across a reading, so a stall that spans one shows as a large max; the clock restarts while the game is paused (the first frame after is not a stall). Pushed only while sampling. CPU tick deltas are taken in 32 bits (the kernel's counters wrap).
- The client trusts nothing in the datagram (`client.md § app`, `PanelText.loadLines`): shares clamp to 100 %, impossible memory is dashes, unknown pressure or heat is "?".
- The game's process: `RunningGame.pid` (`RunningProcess`: the launcher's process id; the fake game: the test process). Its CPU is the share of `ri_user_time + ri_system_time` over the wall time between two readings (centi-cores: 100 = one core); memory = `ri_phys_footprint`. The launcher's child processes are not added. A pid that is gone: `gameAlive` false, fields 0.
- Interfaces (checked against the macOS SDK headers; the list with findings is the header comment of `MacLoad.swift`): `host_processor_info(PROCESSOR_CPU_LOAD_INFO)` (array released with `vm_deallocate`; counted in `MacLoadTests`), `host_statistics64(HOST_VM_INFO64)`, `proc_pid_rusage(RUSAGE_INFO_V6)`, `mach_timebase_info`, `ProcessInfo.thermalState`, `sysctl hw.memsize hw.nperflevels hw.perflevelN.logicalcpu kern.memorystatus_vm_pressure_level`.
- Differences found: a chip can report three performance levels (the fastest first), so "efficiency" = the LAST level and "performance" = all earlier ones (one level: everything is performance). Which logical CPU belongs to which level has no public query: the efficiency CPUs are taken as the first indices. MEASURED (an Apple silicon Mac with three levels, three spinning processes started and stopped by PID, the sampler's own readings, two runs each): at normal priority performance 51 / 55 %, efficiency 3 %; under `taskpolicy -b` performance 0 / 1 %, efficiency 55 / 57 %. The labels are right on that chip; other chips are a device row in `todo.md`. The total never depends on it. Memory "used" = internal - purgeable + wired + compressor pages. Pressure 1 / 2 / 4 map to 0 / 1 / 2.
- GPU: `GPUUtilisation.read()` (own file, called only by `MacLoadSampler`) reads the accelerator's `PerformanceStatistics` "Device Utilization %" from the I/O registry (the one non-API read; deleting the file removes the feature); absent: `gpuPresent` false and the panel says "GPU n/a".
- Tests: `MacLoadTests` (ranges, memory total, own pid, missing pid, 30 samples release 30 arrays, GPU nil), `FrameClockTests`, `HostServiceTests` ("load" section: nothing below full, first within 1.2 s then one a second, frame fields 59...61 fps, off stops, session end stops, slow read), `PacingQueuesTests` (lazy slot), `WireTests` (vector).

#### ltr

- `LtrAcks` (value type, fixed storage of 256 entries indexed by frame number: nothing allocated per frame or per `ack`): for each frame the game sent to the live session, its token (-1 = none), picture size and time, kept 2 s.
- `ack(frame)` from the live session: when that frame is known (2 s), has a token, is of the newest frame's picture size (never a frame of an earlier size once a frame of the new size was seen) and is newer than the last acknowledged frame -> tap `ltrAck([token])`, the token unchanged (opaque: the epoch is in its high bits). An `ack` from a session that is not the live one changes nothing (as every datagram: its address only). Cleared by `clearResends` (a game starts, pauses, exits), not when a session is admitted or ends: a key frame at admission voids older tokens in the tap.
- Not every frame carries a token (about 1 in 14 until acknowledgements flow, every frame after): an `ack` of a frame without one gives nothing.
- `repair` -> tap `refresh`; the game (the tap) decides between a repair frame and a key frame and marks the frame; the Host never guesses which frame answers (frames encoded before the tap read the refresh are still in flight and depend on the lost frame).
- `FrameSizes`: sizes of the newest 1024 ordinary, repair and key frames; `frameSizeMedians` -> `portal-hostd`'s exit line.

#### admin

Calls the Host app makes (`HostService+Admin.swift`; all `await`ed). After `stop()` each does nothing or returns nothing: none starts, launches or publishes anything.

- `devices()` -> `[PairedDevice(id: public key, name, live, shownName, kind)]` sorted by shown name. `PairedDevice.shownNames(peers)`: alias, else the device's name (cleaned again), numbered " 2", " 3" in pairing order (`added`; no date first, in file order) until unique among the shown names and not another device's own name; exact comparison, computed on each call, never stored. `renameDevice(id, to:)`: cleaned, nil or empty removes the alias; allowed while connected, nothing is sent; throws the store's error or `.stopped`. The shown name is what the status line, the remove question and the wire carry: `refuse(.busy(device:))` and `bye(takenBy:)` send it cleaned and bounded again at that moment, whatever the store holds. `removeDevice(id)` unpairs, sends a sealed `bye` to every connection of that device and ends it (`by device-removed`: one session-end line, the game pauses); an unknown device is no error; when the store cannot write, the sessions still end, the store's error is thrown and the device stays in `devices()`; after `stop()` it throws `HostServiceError.stopped`. #### options

Per-game options: the game's own settings, chosen per game by a paired device, kept on the Mac, applied at the game's next start (`HostService+Options.swift`, `GameOptions.swift`, `GameOptionsStore.swift`, `HiddenOptions.swift`). Messages `optionsRequest` / `options` / `setOption` / `resetOptions` (`portalkit.md § wire-network`), admitted phase, in a library session and a playing one alike.

- The list is the game's: `<app>/Contents/Resources/dm/launcher.json` (`GameOptionsReader`, schema 1, unknown fields ignored). Read off the actor, opened without blocking and checked on the descriptor (a regular file, at most 256 KiB, else none); at most 200 rows (`OptionLimits`, `PortalKit`: the one definition of every limit here, the decoder of `options` uses it too); a row needs `env` (`DM_` then `A-Z 0-9 _`, 4 to 64 bytes in all), `kind` and `default`, a number where the schema says text is taken as its text, a range whose `min` is over its `max` or whose `step` is 0 or less loses its numbers (the row stays, read-only: the wire decoder would refuse it), a repeated `env` keeps the first, texts lose control characters (line breaks become spaces) and are cut at 512 characters and 2 KB, an `options` value over 128 bytes or with a control character is not offered. Dropped (no row, so nothing to set; a variable the game lists that is reserved is not kept as an unsettable row): `HiddenOptions.names` (switches that act on the Mac's window, its performance HUD or an iPhone's screen, or that open the Mac's microphone: 10 names, from the runtime's `player` switches in `docs/env_switches.tsv`) and the reserved variables, below.

- Allow-list (`PlayerOptions`): a device can set only a variable in the runtime's `player` class (28 names copied from `docs/env_switches.tsv`; a subset test reads the table where it exists and skips where it does not) minus `HiddenOptions.names` minus `DM_SAVE_SYNC` (a folder, not a row), and only when the game's own list names it and the value validates. A variable the runtime adds later is not settable until it is listed. Checked in the reader (any other row is dropped, not shown unsettable), when a choice is set (`rejected`) and at launch (a stored choice for any other is left out, a hand-edited store included). `HostConfig.settableOption` is the predicate and `optionsAnswerHook` a stand-in's: both are `@_spi(Testing)`, so only a file that says `@_spi(Testing) import PortalHostCore` (a test) can set them; the apps and `portal-hostd` cannot compile it. `portal-hostd --fake --fake-options` serves `FakeArt.sampleOptions`: ten rows, all variables of the allow-list, through the unwidened gate (`testTheTestToolsSampleListPassesTheRealGate`). `ReservedVariables` stays as a second filter at launch: prefixes `DM_STREAM`, `DM_LAUNCH`, `DM_ENV_`, `DM_KEYS` (scripted input), `DM_GAMES_`, `DM_GPU_CAPTURE`, endings `_DIR` `_FILE` `_PATH` `_OUT`, and the 60 `path`-class names. The owner's own `environment.json` is not held to either (it may set what it likes) except `DM_STREAM` and `DM_LAUNCHER`, the Host's. Every row the runtime's own settings list can emit stays settable (`testEveryRowARealSettingsListCanEmitStaysSettable`).
- `validate(value, for:)` (the only judge): no value over 128 bytes or with a control character (line breaks, NUL, C1, U+2028 / U+2029); choice = one of the row's values; toggle = its `on` or `off`; range = a plain decimal (`-`? digits (`.` digits)?, ASCII, no exponent, `nan`, `inf`, sign or space) inside `min...max`, snapped to the nearest `step` and written with the decimals of `min` and `step` ("0.76" is "0.75", "1.0" is "1"). A value goes only into an environment variable, never to a shell.
- Off the actor: the library lookup (a linear scan of the cached list) is the actor's; the file read, the preference reads and the store's file sync run in a detached task (`testASlowPreferenceReadDoesNotDelayVideo`). A saved choice is read as text only (`HostConfig.preferenceText`): the runtime ignores one that is not a string (`frontends.md` § Saved choices), so a number or a boolean is not shown. `portal-hostd` (a manual tool, not an `-auto` run) uses the real reader. No `-auto` run reads a person's preferences: `HostModel` takes the reader, `Automation` gives one that returns nothing (`HostModelTests.testTheSavedChoiceReaderIsTheOneTheModelIsGiven`).

- `optionsRequest(titleID)` -> `options(GameOptions)`: the rows in the game's order with `current` = the app's choice (if the list still offers it and it is not the default), else the app's own saved choice (`launcher.<env>` in the app's bundle ID domain, `HostConfig.savedChoice`, only when it validates), else the default; `chosen` = the app's choice. A title the Mac does not have, or a game with no list, is `settings: []`; nothing is read from disk for a title that is not in the cached library. A title that is not a title ID (1 to 32 letters and digits) is refused on decode and ignored.
- `setOption(titleID, env, value)`: kept only for a row of the game's list, to a value that validates; `value` absent, or equal to the row's default, removes the choice. Answer = `options` with the new state; a set for a game that has no choice yet while the store keeps 64 games answers `full: true` (the app says the Mac is full; nothing is dropped); a refused set (unknown title, variable not in the list, reserved, bad value, store full or not writable) changes nothing and names the variable in `rejected` (the name when it is a name, at most 64 bytes, else empty). `value` nil also removes a stale choice whose row the list no longer has. `resetOptions(titleID)` removes every choice of the game (a title the Mac no longer has too). A running game is never told; the choices apply at its next start. Only the asking device is answered.
- Store (`GameOptionsStore`, `HostConfig.optionsURL`; nil = in memory only, tests and `-auto` runs; the app gives `~/Library/Application Support/nxPortal/options.json`): `{"version":1,"titles":{<title>:{<variable>:<value>}}}`, only values that differ from the default; the file 0600 in a 0700 folder (made 0700 when missing), written by a temporary file and a rename; a change that cannot be written is refused and not kept. At most 200 choices per title (the reader's row limit) and 64 titles of 32 bytes; one cap of 4 MiB for read and write (a write past it is refused), and the limits fit under it (`GameOptionsStoreTests`); the service only accepts rows of the game's own list, so a game never has more choices than it has rows. A file that does not decode is read as empty, left alone until the next `set` and then kept beside the new one as `options.json.corrupt`; a file that decodes keeps only what a `set` could have written.
- Launch: `launchEnvironment(for:)` takes the game's stored choices that the list still offers now (a stale one, a variable gone from the list or a value no longer valid, is left out) and merges: the Host-wide `environment.json` variables, then the choices over them for the same variable, `DM_STREAM` and `DM_LAUNCHER` in neither.
- Hidden names (`HiddenOptions.names`, checked against a real game's list: 4 of its 18 rows): `DM_FULLSCREEN`, `DM_METAL_HUD`, `DM_PICTURE_FIT`, `DM_PRESENT_UPSCALE`, `DM_SHOW_FPS`, `DM_HOME_QUIT`, `DM_TOUCH_HAPTICS`, `DM_SW2`, `DM_ROTATION` (the orientation lock of a game on a phone or tablet itself), `DM_MIC`, `DM_MIC_GAIN` (a streamed game never opens the Mac's microphone; `DM_MIC_DEVICE`, a `player` name not in the settings list, is not listed and so not settable).
- `GameApp.bundleID` = `CFBundleIdentifier` of the app's `Info.plist`. Tests use generated apps, made-up bundle IDs and folders under the temporary one; no test reads or writes the person's folders or preferences.

#### model

`HostModel` (`@MainActor @Observable`) -> `PortalHostModel` (macOS only; no UI): the menu's model. `HostSettings` / `HostSettingsStore` (`HostSettings.swift`), `HostMessages`, `PairingAnnouncing`.

- State: `phase` (`.stopped`, `.starting`, `.running(port:)`, `.failed(text)`), `status` (the service's, `.pairing(code:until:)` shown as is: the model never decides expiry), `devices`, `games`, `message`, `settings` (read-only; changed through `addFolder` / `removeFolder` / `rename`).
- Settings: `HostSettings { name? (nil = the computer's name), folders, maxBitrate (default `HostDefaults.maxBitrate`, passed as `HostConfig.maxBitrate`) }`, JSON under the defaults key `hostSettings`; unreadable data gives the defaults, a missing field keeps the others (`decodeIfPresent`). The pairing store is `HostConfig.secrets` (never a file).
- Roots: `/Applications`, `~/Applications`, then `settings.folders`; a folder twice counts once. A missing folder is refused with `HostMessages.folderMissing`. The default launcher (`launcher: nil`) is an `AppLauncher` that looks a title up in the current roots.
- The person's last word: `wantsRunning` is set by `start()` (true) and `stop()` (false) only; `rename` and the retry loop read it. A `stop()` that lands while `rename` is between its stop and its start wins (name saved, Host stays stopped); `stop(); start(); stop()` ends stopped, `start(); stop(); start()` ends running with one service; `start()` twice or during a retry wait returns at once (no second service, the retry is not hastened).
- One service at a time (hard rule: two pairing stores on one secret store can lose a pairing through interleaved writes). A failed service is stopped completely (awaited) before the next is made; `liveServices` and the injection point `makeService` let a test count.
- Failure: `.failed` from the service, or a `start()` that threw: `phase = .failed(text)`, `message = HostMessages.serviceFailed(text)`, retried every `retryInterval` (phase stays `.failed` until it runs). `stop()` ends the loop during a wait or a start; a start beaten by `stop()` (`CancellationError`), or a `.failed` that reaches the model while `stop()` runs, is no failure: no message, no retry. `devices` / `games` are written only while the same service is `.running`.
- A service that cannot be made (identity unreadable: `PairingStore.init(secrets:)` throws; or the game socket path): `.failed` with its own sentence, NOT retried (retrying cannot cure it); a later `start()` by the person tries again.
- No timeout of its own: a game that takes minutes to show a picture is whatever status the service reports.
- Calls (all `async`): `beginPairing()` / `remove(_:)` on a model that is not running set `message` and do nothing else; `remove` when the store cannot write: the session has ended, the device stays in `devices`, `message` says so (by the shown name); `rename(_ device:, to:)` sets the Host's name for a device (`message` when it cannot be saved). `rename` saves the name and restarts a running service (the network name changes): the restart ends a running or paused game and every session, and `rename` does not refuse, so the app asks first with `gameIsActive` (a game starting, running or paused). `refresh()` re-reads devices and games, as does every status change; a game's run state (`starting` to `running`) changes no status, so the app calls `refresh()` when the menu opens.
- `onEvent` (`HostEvent`): `.listening(port)`, `.status(s)` for every status the service publishes, `.sessionEnd(line)` from `sessionEnds` (consumed until the service has stopped: the last line is not lost), `.failed(text)` once per reason until the service runs again, `.note(line)` (a line from the launcher, as it is); `HostEventLine.text(_, showCode:)` makes the `portal-hostd` line. `show(message:)` lets the app put a line in `message`.
- Announcer: `announce(code:)` once per new code, `withdraw()` when the status leaves `.pairing` (and when the service stops or fails).
- Text: every sentence is in `HostMessages` (`HostServiceError` is a `LocalizedError`: its text is the Host's own, one sentence per case, no identifiers). Logs (`Logger`, category `model`) carry no name, address or key.
- Tests (`PortalHostModelTests`): `MemorySecrets`, a volatile `UserDefaults` suite, `FakeLauncher`, real `ClientSession`s over loopback, a counted `makeService`.

- Reads for the menu: `HostService.sessionDetail()` (fps, rate, the preparing game) is read with the lists on every status change and every `refresh()`; the model sets `status` and the detail in one step (no await between), so a line never pairs a new status with an older session's numbers. While the menu is open the model reads again every 2 s: `HostModel.menuOpened()` / `menuClosed()` start and stop one loop (a second open is ignored; nothing runs closed; tested with an injected clock). Backstop in the model: the view calls `menuStillOpen()` on each refresh it draws (`onChange` of `menuRefreshes`); a loop not re-affirmed for 10 s (`menuLapse`, on the injected `menuNow`) ends by itself ("menu lapsed"), so a close the view never reported costs one lapse. Tests: lapse, just under it, the fps 3 s expiry and 2 s restart (`HostService.reportedFps(atNs:)`), headline back to the game's once preparation ends. The view calls them from its OWN window (`WindowLifetime`: didUpdate while visible, didBecomeKey, occlusion = open; willClose, order-off, covered = closed), never from the app's key window. Debug runs print "menu opened", "menu read <n>", "menu closed" (`-autoWindowClose`).
- Rename restarts the Host and ends a running or paused game: the menu calls `await model.refresh()` and then reads `gameIsActive` (while a code is open the status does not change when a game starts), and asks first ("Rename and End Game") when it is true. The menu reads the service while it is open: `WindowLifetime` (the menu window's open / close, its occlusion and order-off-screen) calls `HostController.menuOpened()` / `menuClosed()`, which start and stop `HostModel`'s 2 s reads; a read re-affirmed for 10 s (`menuLapse`) ends by itself, so a missed close costs one lapse.
- Game Folders window: `/Applications` and `~/Applications` (fixed) and the added folders; "Add…" is an `NSOpenPanel` (folders only), "Remove" per added folder. A folder spelled another way (a link, `/Applications` by hand) is not added twice (resolved paths are compared).
- One instance: the oldest stays. A starting instance exits 0 at once, before anything is opened or written, when another instance is older (`InstanceRule`: an earlier process start time from `proc_pidinfo`, so a pid that wrapped round cannot make a newcomer the survivor; an unreadable start time counts as older; equal times: the lower pid; two starts that see each other leave exactly one; a running instance never re-checks). `SingleInstance` finds the others by bundle ID or by executable path (a binary started by path has no bundle ID in Launch Services). A process already in its stop cannot be told from a running one, so a launch during the up to 12 s of a stop exits. Not applied with `-autoStore`.
- Files, in every build: secrets in `FileSecrets` under `~/Library/Application Support/nxPortal/` (folder 0700 — an existing one with wider modes is tightened at start, `tightenFolder()` —, files 0600), NOT the Keychain (a rebuilt or ad hoc signed app is asked for Keychain permission again; this app is installed on a Mac nobody sits at; the Keychain move is owed before a release: `todo.md`); settings in `UserDefaults.standard`; game logs `~/Library/Logs/nxPortal/<titleID>.log`.
- `environment.json` (optional, same folder): one flat JSON object of strings, read at start and passed for every game (`HostModel(gameEnvironment:)`; the Host's own `DM_STREAM` / `DM_LAUNCHER` win). A game's saves and prepared graphics live under the `HOME` it is started with, and a save-sync folder variable can be set here too (`PortalHostModel.EnvironmentFile`). Absent: nothing. Unreadable, not an object, or a non-string value: the whole file is ignored, one log line and a `message`. No UI for it yet.
- Log: `~/Library/Logs/nxPortal/host.log`, rotated once at 1 MB to `host.log.1` (`HostLogFile`; when the move fails the file is truncated instead of growing): a UTC time, then `listening on port <n>`, `status: …` per change as `portal-hostd` prints it (the pairing line without its code), each `session end: …` line exactly as the Host core makes it (`HostService.sessionEnds`, handed on by `HostModel.onEvent`, so the model's own stop does not lose the `host-stop` line), `failed (<text>)` once per reason, and the ignored-file line. No codes, keys or addresses. `sender:` lines are not printed.
- Quit and signals: "Quit" and `applicationShouldTerminate` stop the Host (`model.stop()`: the game ends with it, killed after 5 s if it ignores SIGTERM: `§ game-launch`) and wait at most 12 s before the process ends; every request joins the one stop (`ShutdownGate`: a second Quit or signal never ends the process before the first stop has finished or its 12 s have passed; its `finally` (the app's cleanup) and the one `reply(toApplicationShouldTerminate:)` each run once); SIGTERM / SIGINT do the same through a dispatch source and `exit(0)` (`NSApp.terminate` from inside that main-queue callback deadlocks: its nested event loop cannot run the stop's main-actor work).
- Notifications: `PairingNotifier` (PortalHostModel; `announce` / `withdraw` only queue work for a task of its own, so the model's status loop never waits for the permission question) over `SystemNotificationCentre` (`UNUserNotificationCenter`): permission asked at the first pairing, title "nxPortal pairing code", body the code, withdrawn with the code. No permission: nothing posted, nothing fails; the code is always in the menu.
- `Automation.swift` (`#if DEBUG`; a Release binary has none of it): `-autoSnapshotDelay <s>`, `-autoWindowClose <s>` (see `build.md`), `-autoStore <dir>` (`FileSecrets`, log and game logs under it; settings from a volatile defaults suite; the real `environment.json` is ignored; notifications are silent), `-autoLibrary <dir>`, `-autoName <name>`, `-autoPair`, `-autoFakeGame <portal-fakegame>` (a `FakeGame.app` under the store whose `nxnative` runs the tool on `$DM_STREAM`, plus the game `FAKE000000000000`), `-autoWindow`, `-autoSnapshot <png>` (SwiftUI `ImageRenderer` of the menu, no screen-recording permission; its text field shows as a placeholder). With any `-auto…` the log lines go to stdout too, flushed per line, with the pairing code and a `pairing code: <code>` line.
- Icon: the doorway drawn by `scripts/make_icons.swift` itself at every Host size (16 to 1024, the macOS rounded-square shape) -> `build.md § icons`.

#### session-end

One line per live session that ends (the game pauses when it does, unless the same device replaced it), on `HostService.sessionEnds` (`SessionEndReport`) and in the log (`Logger`, subsystem `nxportal`, category `session`); `portal-hostd` prints it -> `HostService+SessionEnd.swift`.

```
session end: <tag> after <s> s, by <cause>, datagrams in <n> out <n>, send failures <n>, first datagram after <ms> ms|never, media local address <same|differs|unknown> from control
```

- `<tag>`: the first 8 hex digits of SHA-256 of the device's key (`PairedPeer.tag`); no log line (`session end:`, `status: live <tag>`, any other) carries a device's name. `HostStatus.live(device:tag:game:)` keeps the shown name for the menu only; `HostStatus.logText` is the one status line `portal-hostd` and the log use.
- `after`: from admission. `by`: `client-closed` (the connection closed, or `bye`), `client-silent` (the silence limit), `host-stop`, `replaced` (the same device admitted again), `device-removed` (`removeDevice`), `control-error` (a frame that does not frame, open or decode, or a control connection that ended with an error such as a reset; a clean close by the device is `client-closed`). Every `end` call names its `by`; a connection that was never live prints no line. `media local address` compares with the control connection's local address captured when the session went live.
- `datagrams in`: datagrams of this session that opened (from `welcome`, before admission too); `out`: datagrams the sender put on the wire since admission; `send failures`: sends the socket refused for good (`.failed`; `.wouldBlock` is retried, not counted) -> `MediaSender.sessionTotals`, reset at `attach`.
- `first datagram after`: from `welcome` to the first datagram that opened; `never` when none did.
- `media local address`: the newest datagram's arrival address against the control connection's local address (IPv4-mapped read as IPv4); `unknown` when no datagram came.
- No addresses, keys or session IDs in the line. Reading it: `in` > 0 and `out` > 0 with the device closing at 2 s (`client-closed`, or `control-error` when the connection was reset) = the device heard nothing the Host sent (`client.md § session`); `in 0` = nothing from the device reached the Host; `send failures` > 0 = the socket refused.

#### sender

`MediaSender` (a handle: its thread belongs to `MediaSenderCore`, so a sender dropped without `stop()` ends its thread in `deinit`) over `PacingQueues` (a struct with no thread and no clock: time is an argument, so the tests drive it to the nanosecond). Every datagram to the client goes through it, sealed there.

- One thread of its own (`Thread`, `.userInteractive`) in the real-time class (`THREAD_TIME_CONSTRAINT_POLICY`: period 1 ms = one slice, computation 300 us for a slice's seal and send of a few dozen datagrams, constraint 1 ms, preemptible), sleeping with `mach_wait_until` to each slice (not `Task.sleep`, which coalesces by milliseconds; the earlier dispatch timer woke 350 us late at p95 on an idle Mac, 50 us now, and on a busy one the hop is what made the client's tail rule ask for nothing lost). An `NSCondition` wakes it when work arrives while it idles; it catches up after a late wake by sending every slice due. The queues, sealer, address and counters sit behind that one lock; `@unchecked Sendable` for that reason only. The socket never blocks, so the lock is held for at most one slice's sends. An urgent datagram is sealed and sent inline by the caller under the lock (on the wire when `enqueue` returns, no thread hop); only one the socket refused, or one queued behind a refused one, waits for the thread.
- A fourth, one `lazy` slot (the Mac's load): the newest replaces the one waiting; it leaves only when no resend or video waits and nothing urgent waits, a refusing socket keeps it one slice, never retransmitted. Three queues, served in this order: `urgent` (pong, sound, `hostStats`: leaves at once, never waits for a slice), `resend` (at most 32 datagrams a 1 ms slice, before that slice's video; a late wake-up gives the slices missed, up to 4), `video`.
- Video: frames in order. A frame of 8 datagrams or fewer, or any frame at `HostConfig.paceMs` 0 (`portal-hostd --pace-ms`, 0...16, default 4), leaves at once (a small frame still waits for the frame ahead of it). Else its window is `max(paceMs, bytes / (pacePeak x video rate))` (`HostConfig.pacePeak`, default 3, `portal-hostd --pace-peak 1...20`): no frame leaves faster than 3 times the video rate, and the window is not capped at the frame period, so a large frame takes longer and the frames behind it wait (a key frame of 4 x the average frame takes 4/3 of a frame period; 20 x takes about 110 ms at 20 Mbit/s). The datagrams are spread evenly over `window / 1 ms + 1` slices of 1 ms, the first at once. A late wake-up sends the slices that are due: the schedule never shifts, so no two slices of a frame are more than about a millisecond apart (the client re-asks a frame quiet for 4 ms: `portalkit.md § video`). A frame still leaving when the next arrives keeps its place; the next begins after its last slice, at the same peak (a backlog drains at up to 3 x). Video rate = what the tap was told last (`setStream` with every `config`, so it follows the client's `rate`; a frame queued before the change keeps the window it was given).
- Capacity is not the sender's to create: a stream at 91 % of a link cannot take a 4 x key frame however it is spread (`portalkit.md § test-network`, `narrow`); the client's rate controller (`client.md § rate`) starts a session at half its ceiling and cuts below what the link delivers.
- A key frame drops the frames before it that have not begun (they would only delay it: the client discards them; a slow key frame behind them made the client ask for a second one, which doubled the load: `bursty` collapsed in one run of four before this).
- Backlog: more than 100 ms of sending queued behind the frame now leaving (the sum of the windows of the frames after it; a long key frame does not count against the frames behind it) drops the oldest frame not begun, whole; never a key or repair frame (a restart point: `restart`), never one begun. Every dropped frame (backlog or superseded) is counted (`framesDropped`) and removed from `ResendStore`, so a `nack` for it finds nothing (`unknownFrame`) and the client gives up and asks for a refresh.
- A `wouldBlock` leaves the datagram at the head of its queue, already sealed (sealed once: no counter is burned by retries), and stops the sending until the next slice (urgent: one slice after the refusal, never at once: no spin); nothing is dropped. Small frames count one slice each towards the 100 ms backlog, so a blocked socket cannot grow the queue; frames that vanish with `discardQueued` are counted as dropped.
- Sealing: at send time, on the sender, in the order datagrams leave. The receiver's replay window is 64 counters (`portalkit.md § sealing`); three queues overtaking each other would push a counter out of it if sealed at enqueue. The sealer (counter 0) is handed over at admission (`attach`) and dropped when the live session ends (`detach`: queues forgotten, nothing leaves). A new game (`clearResends`) forgets queued video and resends too.
- `hostStats` (0x29): once a second to the live session from the 100 ms tick: frames from the game (`framesFromGame`), frames fully handed over (`framesSent`), frames dropped by the sender, resend datagrams sent, the video rate, and `sendLateMaxUs`: the worst time a sending slice left late against its schedule in the last second (the first slice of a burst is due when its work was enqueued, so the wake-up counts). Counts since the session began.
- `load` (0x2B): while the live, playing session's `liveSettings.panel` is `full`, once a second; `-> § load`.

#### hostd

```bash
portal-hostd --library <dir>... [--store <file>] [--name <name>] [--port <n>] [--pair] [--fake [--fake-shelf] [--fake-options] [--fake-prepare <s>] [--fake-white]] [--max-bitrate <Mbit/s>] [--pace-ms <ms>] [--pace-peak <x>]
```

- Defaults: store `~/Library/Application Support/nxPortal/host.json`; name = the Mac's computer name; port any; advertises.
- `--pair` prints `pairing code: <code>`; prints `listening on port <n>`, `status: …` per change (`status: failed (<text>)` exits 1) and `session end: …` per ended live session (`§ session-end`). `--fake`: `FakeLauncher` + one game `FAKE000000000000`, its icon drawn by `FakeArt` into a temporary folder removed at exit; `--fake-shelf` adds six placeholder games (`FAKE000000000001`...`6`: one not streamable, one without an icon) for library screenshots; `--fake-options` gives the fake game a made-up `launcher.json` (`FakeArt.sampleOptions`: ten rows, two sections, a render-scale range with a `base`, a `needs` row, a kind nobody knows) for screenshots of the per-game options; `--fake-prepare <s>` makes the fake game prepare for that long (three `prepare` spread over it, so progress shows for 5 s after each and "waiting" between) before its first picture; `--fake-white` makes every picture white (screenshots of the trouble screens over the worst picture).
- `--fake` prints `fake game input: buttons=0x<8 hex digits>` once per change of player 0's buttons (via `FakeLauncher.onButtons` / `FakeGame.onButtons`; none for sticks or motion, none with real games).
- `--max-bitrate <Mbit/s>` (1...1000) sets `HostConfig.maxBitrate`, the most a client may ask for (default `HostDefaults.maxBitrate`, 200 Mbit/s).
- `--shape <profile> [--seed <n>]` (development): a `LinkShaper` listening on every interface (IPv6 dual-stack) stands in front of the media port; `welcome` advertises its port (`HostConfig.advertisedMediaPort`), it forwards to the real media socket on loopback and learns the client's address from the first datagram. Prints `shaper: profile=<name> seed=<n>` at start (`random`: a fresh seed unless `--seed`; the others default to 1) and `shaper: forwarded=<n> dropped=<n>` at exit (Host to client). An unknown name lists the valid ones, exit 64. -> `build.md § shaped-host`
  - The hook in the product target is `HostConfig.advertisedMediaPort` (nil = the media socket's own port, today's behaviour) and `HostService.mediaPort`; `PortalHostCore` never imports the shaper (`portal-hostd` depends on `PortalTestSupport`, like `portal-fakeclient`).
- `--pace-ms <ms>` (0...16, default `HostConfig.defaultPaceMs` = 4) sets `HostConfig.paceMs` (`§ sender`); 0 sends every frame at once. `--pace-peak <x>` (1...20, default 3) sets `HostConfig.pacePeak`. At exit: `sender: slices=<n> late_p95_us=<n> late_max_us=<n>` (how late the slices left, whole run) and `frames: median_bytes=<n> repair_median_bytes=<n> repairs=<n> key_median_bytes=<n> keys=<n>` (`§ ltr`).
- Prints `notes` lines (`game prepare: …`, an unknown tap message type) as they come.
- Game logs: `~/Library/Logs/nxPortal/<titleID>.log`. SIGINT / SIGTERM -> `stop()`, exit 0. No addresses or keys in output.
