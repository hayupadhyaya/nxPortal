# Client

The client: `PortalKit/Sources/PortalClientCore/` (session, stats; macOS, iOS, tvOS: Network.framework and Foundation only), `PortalKit/Sources/PortalPlayer/` (decode, sound, input, settings, store, discovery, model: everything but the views) and the app in `Client/` (views, automation) -> `§ app`; `portal-fakeclient` -> `§ fakeclient`.

#### session

`ClientSession` (actor) -> `ClientSession.swift` (calls, control), `ClientSession+Media.swift` (datagrams, timer, input), `NWLink.swift` (one `NWConnection` as an ordered byte/datagram stream).

- Inbound control bytes and datagrams reach the actor through ordered streams, one long-lived task each; no task per packet.
- Order: `connect` (TCP) -> `pair(code:)` (optional, same connection) -> `open(host:)` -> `list` / `launch` / `resume` / `quitGame` / `send`.
- `open`: clear `hello`; `welcome` -> keys derived on arrival (`SessionKeys.derive(role: .client)`); UDP to the TCP peer's host on `udpPort`; sealed `ready`; then waits for the Host's proof (see below); then the first `ping`.
- `arts`: every sealed `art` message as an `ArtChunk`, whether or not an `expect` waits (`bufferingOldest(32)`); `requestArt(titleID:hash:)` sends `artRequest`. Other replies still go through `expect`.
- `optionReplies`: every sealed `options` reply (the answer to any of the four option messages, none is `expect`ed; `bufferingOldest(32)`), the same route as `arts`; `optionsRequest(titleID:)`, `setOption(titleID:env:value:)` (`value` nil removes the choice) and `resetOptions(titleID:)` send. Library and playing sessions alike.
- Host's proof: `welcome` is in the clear and spoofable; `open` returns only after the first sealed frame from the Host opens (the `gameState` sent on admission, also yielded on `states`). None within the reply timeout (5 s; internal `replyTimeout` init parameter) -> `ClientError.timeout` and the session is shut down. Before `welcome`, a clear `gameState` or `bye` is ignored.
- `end: SessionEnd?` (`.local`: `close()` or an unproved `open`; `.hostClosed`: `bye`, connection end, bytes that do not open; `.silence`; `.mediaPathSilent`: the 2 s rule below), set before `frames`, `audio`, `states` finish.
- `requestKeyframe()`: assembler awaits a key frame (`FrameAssembler.awaitKeyframe`: repair frames are no restart point until a key frame decodes), any repair wait ends, `keyRequest` now (at most one per 100 ms), the timer repeats until a key frame yields; deltas are not yielded meanwhile.
- `frameDecoded(_:)` / `decodeFailed(_:)`: the player's decoder's outcome for a yielded frame -> `§ repair`.
- `markDisplayed(captureNs:at:)`: records a hand-off to the display at the caller's `uptimeNs()` (public; same clock as the marks) -> `SessionStats.framesDisplayed`, `p95DisplayMs`.
- Reply waits (`waiters`, oldest first): a message resumes the first that accepts it, so overlapping calls each get their reply; 5 s -> `ClientError.timeout`; connection ending -> `.closed` for all. `refuse(r)` -> `.refused(r)`; a `pairResult` other than `.ok` -> `.pairing(r)`.
- The Host closes an unadmitted connection after 10 s without progress: connect when the code is in hand (or reconnect before `pair`).
- `launch`, `resume`, `quitGame` do not wait; outcomes arrive on `states`.
- Connection end (any cause) sets `end` and finishes `frames`, `audio`, `states`; continue with a new session (same identity: no code needed).
- Media path (the 2 s rule): no datagram from the Host has opened 2 s (`mediaPathNs`) after the media started (`open()` done, the first ping out; 10 pings a second, so an answer is due within a round trip) -> the session ends `.mediaPathSilent` (no `bye`), whatever the control connection does. The Mac answers on control but its datagrams never reach this device (on a Mac with several addresses, an answer from an address other than the one the device sent to is dropped by its connected UDP flow: `host.md § service`). Once one datagram has opened, only the silence limit below ends the session (a stall never ends it at 2 s).
- Silence: once `open()` has completed, `silenceTimeout` (init, default 10 s: `ClientSession.defaultSilenceTimeout`) without an inbound datagram or control frame that opens ends the session (streams finished, no `bye`): the Host's close may never arrive. The Host's pongs (to 10 pings a second) keep an idle session alive.
- Stalled: `stalls: AsyncStream<Bool>` says `true` after 1 s (`stallAfterNs`) without any datagram or control frame from the Host, `false` at the next one. Recovery restarts the video stream (`restartVideo()`: the assembler's held frames are from before the stall and are never asked for) and sends one `keyRequest` (retried every 100 ms until the key frame is in). Pings and the inputs the model sends (neutral) go on while stalled. After a recovery, for 5 s (`staleWindowNs`), sound blocks and video fragments whose capture time (the Host's uptime clock mapped by the ping offset; no offset yet, no filter) is before the recovery moment are dropped: a radio that kept what it could not deliver releases it at once, and a key frame made before the stall is not the answer to the refresh (frame numbers cannot tell them apart: the Host's go on across the stall). The pure rule is `silenceState(nowNs:lastHeardNs:silenceNs:)`. Recovery after `silenceTimeout` is the `.silence` end as before (no auto-reconnect in the session; the app's retry loop below).
- A session dropped without `close()` lets go: tasks hold it weakly, `deinit` cancels both links, the Host sees the connection end.
- `close()`: sealed `bye`, both connections cancelled, idempotent. The Host then pauses the game.
- Timer (8 ms, absolute deadlines): re-sends the latest input per player with a new `seq` (a neutral one rests after it has gone out 5 times, `neutralRepeats`; any new input starts it again; `send` before the keys exist sends nothing); `ping` every 100 ms (`pingEveryNs`; the rate's ping floor needs 2 pongs in 300 ms); `keyRequest` every 100 ms while a key frame is awaited; `repair` every 35 ms while a restart point is awaited, and the escalation after 1 s (`§ repair`).
- Rate (`§ rate`): with a `bitrate` and `adaptiveRate` (init, default true) the session owns a `RateController` with that ceiling; its start rate goes in the `hello` (`Hello.startBps`, the controller's `rateBps` when the hello is sent: the Host has it from admission, so the game's first config carries it whatever arrives first) and again as `rate(start)` when the media starts (after the Host's first sealed frame; a repeat for the Host), a rate sample every 200 ms from the timer and at once on `.refresh` (before the `keyRequest`), the newest `rate` again once a second and after a recovery from a stall (before its key request). `currentRate` (nil when fixed). `adaptiveRate: false` keeps the wish as a fixed rate (tests of the wish path, the pacing scenarios).
- Video: `FrameAssembler` (`portalkit.md § video`): `.frame` yields, `.nack` -> a `nack` datagram, `.refresh` -> `repair(lastGoodFrame:)` when the assembler `acceptsRepair` (a key frame decoded since the decoder last started or failed) and no key frame is awaited, else `keyRequest(lastGoodFrame:)`, at once (`§ repair`; the Host rate-limits key frames to one per 100 ms; the timer repeats the request every 100 ms until a restart point comes out). Sound: only a `seq` newer than the last delivered is yielded. `hostStats` -> `SessionStats.host` (the newest).
- Repair timer: one task, started by a fragment that leaves `nextTickNs` non-nil (a hole, or an open tail: so every frame on a clean link arms it), sleeping until `nextTickNs` (at least 0.2 ms, tolerance 0.1 ms: the default lets the system coalesce the wake by milliseconds), calling `tick`; it ends itself when `nextTickNs` is nil (one task, not one per datagram). A deadline earlier than the one it sleeps to (a hole seen after its frame's first ask) replaces it: the old task, by generation, stops at its next step. `rttNs` = the median ping round trip, 4 ms before the first pong.
- Tail rule: the session keeps the arrival time of the newest Host datagram of any kind (`newestHostNs`) and passes it to the assembler's `tick` / `nextTickNs` (`portalkit.md § video`); a non-video datagram ticks the assembler while a tail is open.
- New game: a sealed `gameState` with run `idle` or `starting` starts a fresh video stream (`FrameAssembler.restart()`: awaiting a key frame, no holes, no `nack` state, repair counts 0; key wait cleared, `lastGoodFrame` 0, the stats' last frame number forgotten so the restart is not counted as skipped): the tap numbers frames from 0 per game process; the Host does not renumber. Sound `seq` is the Host's per session, so it does not restart.
- The UDP connection (media) has `NWParameters.serviceClass = .interactiveVideo`; the TCP control connection stays best effort.
- Datagrams over 1,200 bytes or that do not open are dropped. Streams are unbounded (dropping a frame breaks the decode chain).
- Test hooks: `dropVideo(_:)` (public): video fragments the predicate returns true for are dropped on arrival, as if lost on the link (a test link cannot read a sealed fragment's frame or mark); `setIncomingDatagramFilter` (internal): index of each incoming datagram, `false` drops it; `mediaFrom` (internal init): the local address the media link sends from (`NWParameters.requiredLocalEndpoint`), so a test reaches the Host at one address from another.
- `setSendObserver(_:)` (internal): sees every datagram the session sends before it is sealed, so `SessionSendRulesTests` can assert a cut's three sends, the first-second give-up rule, and the order rate -> key request after a stall and rate sample -> `repair` (no link needed).

#### rate

`RateController` (`PortalClientCore/RateController.swift`): a value type with no clock (time and samples from the caller); `update(RateSample) -> UInt32?` (the new rate when it changed). The user's bitrate is the ceiling; the Host clamps again (`host.md § service`).

- Sample (`RateSample`, the session every 200 ms and at once when the assembler asks for a refresh): frames given up (only those settled: 150 ms after the give-up with no late fragment of them, `FrameAssembler.settledGiveUps`; a delayed burst is not a shortage; none in a stream's first second, when the first key frame is all there is; every give-up since the last sample, settled or not, only for `frozen`), fragments asked for again, video fragments received (resends included), frames completed, payload bytes received, the delivered rate over the last 300 ms (50 ms slots), what the encoder produced over the last second and over the last 300 ms (each frame's size from its first fragment: `(count - 1) x max payload` plus the last's size, or half a payload when unseen; lost fragments included), the ping floor (`StatsTracker.rttFloorNs`: the lowest round trip of the pongs of the last 300 ms, nil under 2; a gap of over 150 ms between pong arrivals, counted from the newest arrival before the window or else its start, is a pause: pongs sent before its end are not used, since they measured the pause, while a queue keeps the cadence), the median ping round trip. Delivered and produced are 0 (unknown) in a stream's first 300 ms. A sample more than 1 s after the one before, or with nothing received (a stall), is no evidence: nothing changes, the clean stretch starts again (not for an empty sample under 100 ms after the one before: a refresh sample is just short). The loss window is a ring of 64 samples.
- Frame delay (capture to arrival) is no signal: a busy picture raises it with no queue anywhere. Pings go 10 a second so the floor has 3 pongs in its 300 ms; a queue on the way (one downlink) delays every pong.
- Start: half the ceiling, not under 10 Mbit/s unless the ceiling is.

| Rule | As built |
|---|---|
| Loss trouble | `givenUp`: 2 or more frames given up in the last second (while the sample has one); `loss`: asked / received over 10 % in the last second (while the sample asks), or over 20 % in one sample of at least 100 fragments |
| Queue trouble | `queue`: the ping floor more than `max(15 ms, 2 x minimum)` above its 30 s minimum (per-second minima) |
| Link-limited | loss trouble, the encoder producing at least half the rate over the 300 ms window, and delivered under 0.9 x that: only then is the delivered rate the link's (a quiet or just-changed picture delivers little on a good link) |
| Cut | `0.7 x rate`; link-limited: `min(0.7 x rate, 0.85 x delivered)`; never under `0.7 x produced (1 s)` unless link-limited or `frozen`, and never at or above the rate (then `0.7 x rate`); floor 2 Mbit/s |
| Hold | no further cut until `max(400 ms, 4 x rtt)` after the Host could apply it (half a round trip, plus what is left of its 250 ms between configs after the change before); no increase for 5 s |
| Inside the hold | 200 ms or more after a cut: `measured`: loss trouble with delivered since the cut under half the rate and link-limited -> 0.85 x that; `frozen`: loss trouble with frames still given up (settled or not) and none completed (the refresh did not fit) -> 0.7 x again |
| Any increase | only after a clean second in which the encoder produced at least half the rate (a quiet picture proves nothing about the link) |
| Climb, before any trouble | `climb`: + 25 % per clean second (50 -> 100 in about 4 s) |
| Memory | the rate when a trouble episode began (an episode: trouble after at least 1 s clean; cuts while it goes on do not change it); a rate that never ran clean for a second with demand (the start, a climb step, a quiet picture, a probe) is no memory and never raises one (an existing memory stays; link evidence may lower it); with none, the memory is what the link delivered when it is the limit, else (no link evidence: a transient, a queue, a quiet picture) the rate the episode began at, and any later link-limited sample of the episode lowers it as below; trouble below the memory sets it to the rate, or to the delivered rate when link-limited and lower; in such an episode a later link-limited cut lowers it to that delivered rate too (its first cut may be a queue's) |
| Climb back | `climb`: to 90 % of the memory (rounded to whole bit/s, else the rate stops under it and never probes) in 4 equal steps, one per clean second |
| Probe | `probe`: after 30 clean seconds with the encoder at 0.9 x the rate or more, + 5 % every 5 clean seconds; trouble there is a new episode |
| Fade | 60 full, clean seconds above the memory (encoder at 0.9 x the rate or more) in total: forgotten, the fast climb again. A quieter second pauses the count; trouble resets it |
| Full demand | proving a rate (`rateRanClean`), probing above the memory and the fade count only while the encoder fills 0.9 x the rate: a quiet picture proves nothing about the link |
| Burst loss | a loss with no link evidence and no queue under a measured memory cuts but leaves the memory (a guessed memory, the episode's starting rate, is lowered once by such a loss and is measured from then on) |

- The ceiling the model sends (`liveNow`) is never under `RateController.floorBps` (2 Mbit/s); the Host's own floor is 1 Mbit/s, so the client's larger one wins. `setCeiling(_:)` (the user changed the bitrate setting while the session runs; `ClientSession.sendLive`): a ceiling under the rate makes it the rate at once and returns it (not a cut: no trouble, so no hold, no cut count, the memory stays; `reason` `start`; the session logs it and sends it as a cut goes out); a higher ceiling changes nothing now, the rate rises by the rules above only (a memory above the lowered ceiling does not make it jump: the climb back is in equal steps from the last cut's rate). Never under the 2 Mbit/s floor.
- `SessionStats.load` / `loadAtNs`: the newest `load` datagram (Host, only while the panel is at "full") and when it arrived; `PlayStats.load` is it while fresh (3 s), else nil; the panel's Mac and Game blocks (`PanelText.loadLines`: CPU and GPU with eight-cell bars `PanelText.bar`, performance / efficiency, memory with pressure and heat, the game's CPU, memory, fps and frame times) show dashes without it, "GPU n/a" when the Mac gives no GPU reading, dashes on the Game lines when the game is not running (`host.md § load`). Nothing in the datagram is trusted: shares are clamped to 0...100 % (the game's CPU is of ONE core, so it may pass 100; over 256 cores is dashes), memory with a zero or absurd total or used above total is dashes, an unknown pressure or heat reads "?" (never a state), fps above 1000 is dashes; a datagram of the wrong length or with unknown flag bits does not decode and is ignored. The game's fps cell says "paused" / "starting" (`PanelText.note`, from `gameState` and `preparing`) or "no frames" (running, none arrived: stalled); the frame line carries ms on every figure. Placement: `TouchPanel.frame` takes the MEASURED size (`NumbersPanel.onSize`): controls shown, top centre under the centre row; hidden, top left and moved below the gear where it would reach it; tested with `estimatedSize` of every level against every control and the gear on five screens.
- `SessionStats.rateBps` / `rateCeilingBps` / `rateCuts` (`§ stats`); the panel shows what the Host applied (`hostStats.rateBps`) against the ceiling.
- A cut goes out 3 times, 30 ms apart (the link is congested when it is sent; the Host ignores a rate equal to the applied one); every rate again once a second.
- Every change is logged (`RateController.reason`, `RateChange`, the newest 32 in `SessionStats.rateChanges`, the first `start` at media start): its time from the media start, from / to, why (the `code` names in the table), the ping floor's minimum and the floor, delivered and produced; `RateChange.line` is the app automation's `rate t=` line (`§ app`).

#### repair

A frame given up is repaired from a long-term reference where the game's encoder can (`host.md § ltr`, `tap.md § ltr`); the client decides what to ask for, since it alone knows its decoder.

- Restart point: a complete key frame, or a frame the tap marked repair (fragment flags bit 1) while `FrameAssembler.acceptsRepair`. After a given-up frame the output restarts at the first one; the frames in between are dropped and counted (`framesWaited`), never decoded and never given up one by one; the decoder is not flushed at a repair frame.
- `acceptsRepair` is set by `frameDecoded` of a key frame and cleared (`awaitKeyframe`) whenever the decoder's state is in doubt: session start and a new video stream (`restartVideo`: a new game, a recovery from a stall), `decodeFailed` (a frame the decoder refused, a repair frame included, or a decoder made again: the model resets it on leaving `.playing` and the next delta fails), and an escalation. Until then a give-up asks for a key frame (`keyRequest`) straight away.
- Give-up with `acceptsRepair`: `repair(lastGoodFrame:)` at once (after the rate sample), repeated every 35 ms (`repairRetryNs`, two frame times at 60; a repair frame is ordinary-sized, so asking again costs little) while no restart point has come out; fragments of a key or repair frame newer than the last good frame arriving hold the repeat until 35 ms after the last of them (a key frame from a game without long-term references takes longer than 35 ms to arrive, and asking again would make it send another). A frame given up during the wait (in practice the restart point: the other frames are dropped unasked; a malformed fragment also gives up its frame) is taken for a restart point lost on the way: `repair` is asked again at once (`givenUpSeen` against the assembler's `framesGivenUp`; `restartVideo` zeroes both; proof `RepairTimerTests`). Escalation, a safety net: no restart point 1 s (`escalateNs`) after the first `repair` -> `requestKeyframe()` (a key request, repeated every 100 ms, `keyRetryNs`; repair frames refused until a key frame decodes), counted in `escalations`. The cases that need a key frame get one at once (below), so a timed key request is the last resort: a key frame is the worst thing to ask of a link that just lost frames.
- The game coalesces: a `refresh` while the previous repair frame is still to be encoded or in the encoder is served by that frame (the tap: `stream_video_refresh` sets the request only when no key or repair frame is in the encoder); the Host passes every `repair` on (20 ms limit). Some 25 refreshes in a row with no new acknowledgement (every repair frame lost) may be answered by the encoder with a key frame.
- A key or repair frame coming out ends the wait.
- `frameDecoded(_:)` (the player calls it after the decoder's callback reported a picture): `ack(frame:)` to the Host, at most 30 a second (`ackEveryNs`), always for a key frame and for a repair frame; never for a frame that was assembled but not decoded. Without a player that reports decodes (`portal-fakeclient` without `--decode`), nothing is acknowledged and every give-up asks for a key frame. The rule is `DecodeReport.step` (`PortalClientCore/DecodeReport.swift`, once): the player's pump, `--decode` and the scenario harness (`StreamScenario`'s `decoder:`) all go through it.
- `decodeFailed(_:)`: counted (`decodeErrors`), then `requestKeyframe()`.
- Proof: `AckRuleTests` (ten frames decoded inside 33 ms: one `ack`, plus one each for a key and a repair frame); `RepairTests` (a refused repair frame's token never reaches the game; a lost frame repaired with one repair frame and no key frame; repair frames lost -> escalation then a key frame; a game without long-term references -> a key frame; a repair frame the decoder refuses -> a key frame), the repair gates in `ScenarioTests` (`portalkit.md § test-network`), `VideoDecoderTests.testARepairFrameDecodesAfterLostFramesWithoutError` (a repair frame and every frame after it decode on a decoder that never got the 4 frames lost before it; the control without the refresh fails).

#### decode

`VideoDecoder`, `DisplaySample` in `PortalKit/Sources/PortalPlayer/` (builds for macOS, iOS, tvOS; tests macOS only).

- `decode(_:)` is synchronous and in call order: `VTDecompressionSession` without the async flag, no temporal processing; the picture is collected from the output handler before return.
- Output: `420YpCbCr8BiPlanarVideoRange`, IOSurface-backed; hardware decoder when available.
- Format comes from a key frame's VPS/SPS/PPS (`HEVC.parameterSets`); the sample carries only the picture NAL units.
- A key frame with other parameter sets or another size makes a new session.
- nil (the caller reports `decodeFailed`: a key frame is asked for): delta with no session, malformed data, or a failed decode; a failure drops the session until the next key frame. A repair frame is decoded like any delta (the session is kept).
- `reset()` drops the session. `DisplaySample.make` wraps a picture with `DisplayImmediately` set.

#### sound

`JitterBuffer`, `AudioOutput` in `PortalKit/Sources/PortalPlayer/` (builds for macOS, iOS, tvOS; tests macOS only).

- Frame = 2 `Int16` samples; block = 240 frames = 960 bytes LE; `fadeFrames` = 48 (1 ms), linear ramps; defaults target 1200 frames (25 ms), max 4800.
- `AudioOutput` maximum = target + 2400 frames (50 ms), never under 4800 (100 ms): 25 ms -> 4800, 75 ms -> 6000, 100 ms -> 7200 (room above the target at every setting).
- Filling (start, after every underrun): `pull` writes silence until `bufferedFrames >= target`; the first 48 frames played after are ramped up.
- Underrun: `pull` with fewer frames than asked plays them, last 48 (or all) ramped to 0, then silence; `underruns += 1`; back to filling.
- Gap (`seq > last + 1`): `lostBlocks += seq - last - 1`; last 48 buffered ramped down (if that many), first 48 of the new block ramped up; no silence inserted.
- `seq <= last` dropped; the first `seq` is accepted whatever it is; no wrap handling. A block not exactly 960 bytes is dropped.
- Overflow (push would pass max): oldest frames dropped down to target, first 48 remaining ramped up (only when already playing).
- `AudioOutput`: `AVAudioSourceNode`, float32 48 kHz 2-channel non-interleaved; render pulls into a preallocated scratch under an `OSAllocatedUnfairLock`, no allocation.
- `bufferMs` clamped 10...100, `target = bufferMs * 48`. `start()` twice and `stop()` before `start()` are harmless.
- `start()` decides by `engine.isRunning`: restarts a stopped engine, attaches the node once.
- Recovery: while started, `AVAudioEngineConfigurationChange` (all platforms) and, on iOS/tvOS, session interruption `.ended` and media-services-reset restart the output (session re-activated first); a failed restart is retried on the next notification or `start()`.
- `JitterBuffer.setTarget(frames:)` (under the render lock `AudioOutput` already holds): raised = nothing now, the next refill waits for it (no silence into playing sound); lowered while playing and over the new target by more than one block = exactly the lowering (old target - new, at most the surplus) is dropped from the oldest, the new head ramped in, so a burst's cushion above the target stays (otherwise nothing; filling trims nothing). `push` returns false for a block whose `seq` is at or below the last (dropped, nothing counted) or a wrong size.
- Automatic (`AudioOutput(automatic: true)`, the default setting): `SoundBufferTarget` (pure, time passed in; `PortalPlayer/SoundBufferTarget.swift`) is fed in `push` with each accepted block's arrival time (a block at or below the last `seq` is not an arrival) and with each new underrun; `buffer.setTarget` follows it. Measured = the LARGER of (a) the 99th percentile of the gaps between consecutive arrivals over the last 5 s + 10 ms and (b) the second-largest gap of the last 30 s + 5 ms ((a) cannot see a rise that comes once every 10 s, under 1 % of the gaps; (b) sees it from the second one; a single outlier in 30 s is still ignored). (b) is stored as the two largest gaps of each of the last 31 seconds (32 buckets of 3 numbers, no gap list). Base clamped 20...100. A gap over 500 ms (a pause, a stall, the start) is not a measurement and STARTS OVER: both windows emptied, 50 ms again until 1 s of new arrivals exists, and an underrun within 1 s after it (or one seen after more than 500 ms without arrivals: the pause's own starvation) adds nothing. An underrun adds 10 ms at once (each further one adds again), all held until 30 s after the newest, then they leave through the same down-slew; the sum is clamped to 100. The value moves up at once and down at most 5 ms a second (the slew starts with the first measured value, not from the 50 ms start). `maxFrames` is sized once for 100 ms (7200). The sort runs outside the render lock (own lock; the render thread takes only the lock it took before). `stop()` returns to 50 ms. `AudioOutput.targetMs` = the current target.
- `stop()` resets the buffer (empty, filling, no last `seq`, counters zero): a new stream may start at any `seq` on the same output.
- `JitterBuffer.reset()` does the same reset.
- iOS/tvOS `start()` sets the session to `.playback`, 5 ms preferred I/O buffer, active; macOS has no session.
- A `start()` that throws keeps `wanted` and its observers: the next configuration change, interruption end or route change brings the output up. iOS/tvOS `stop()` deactivates the session with `.notifyOthersOnDeactivation` (other apps' sound resumes). Tests: `failNextStartForTesting`.

#### input

Equal to nxnative's `pad_apple.h`, `front_mac.m` `pad_read`, `motion_apple.h`, `motion_fusion.h` `motion_phone_to_switch`, `DmGamepad.m` `phone_motion_start`.

- `PadMapping.buttons`: `auto` = `usesPrintedLabels` (printed A/B/X/Y where the console's are: Apple's `productCategory` "Switch Pro Controller" or containing "Joy-Con") maps name for name, any other pad by position (`buttonA` bottom -> B, `buttonB` right -> A, `buttonX` left -> Y, `buttonY` top -> X); `byLabel` / `byPosition` force one.
- Shoulders -> L / R; trigger value > 0.25 (strict) -> ZL / ZR; `menu` -> Plus; `options` -> Minus; stick clicks -> StickL / StickR; d-pad -> Left / Up / Right / Down.
- `PadMapping.axis`: NaN 0, clamp -1...1, times 32767, truncated toward zero (0.5 -> 16383). y axes as GameController gives them (up positive).
- `MotionMapping.device(orientation:)` (UIInterfaceOrientation raw): 3 -> (-y, x, z); 4 -> (y, -x, z); 2 -> (-x, -y, z); else unchanged; acceleration and rotation alike; frame `.switchDevice`. `.controller` samples are unchanged.
- `InputMixer` (pure): no pad -> buttons 0, sticks 0; `pad(nil)` also drops the controller's motion. Motion: `never` controller only, `always` device only, `auto` the controller's sample while it is younger than 500 ms (`controllerFreshNs`, time passed in as `atNs:`), else the device's; neither -> nil. `current` is player 0, seq 0.
- `ControllerInput` (`@MainActor`, only GameController / CoreMotion code, no unit test): first controller with an `extendedGamepad` (`GCController.current` preferred); connect / disconnect / become-current observed.
- Disconnect of the controller in use: `mixer.pad(nil)`, send at once, then adopt another one if connected.
- Controller motion from `GCController.motion` when `hasRotationRate`; sensors turned on when `sensorsRequireManualActivation` and off again by `stop()`; acceleration = gravity + user acceleration when available.
- iOS only: `CMMotionManager` device motion at 100 Hz on its own queue unless `deviceMotion == .never`; acceleration = gravity + userAcceleration, rotation = rotationRate; `interfaceOrientation` defaults to 1.
- `controllerName` = `vendorName` of the controller in use, nil when none.
- Device motion: a sample counts as news only when it changes the mixed state (mode `never`, or `auto` with a live controller sensor: nothing is sent).
- `sendCurrent()` sends the mixer's present state now; the view wires it to `ClientModel.onInputWanted` and calls it on appear (play begins and a reconnect completes with a new gate: the Mac holds no input yet).
- Menu chord (`settings.menuChord`, `.plusMinus` default): `menu` and `options` held together 0.5 s (`menuChordHoldNs`) -> `onMenuChord` once per hold (re-armed when either is released); the two buttons still reach the game. `.off` never fires.

#### stats

- `StatsTracker` (value type, no clock) behind `SessionStats`; local time = `CLOCK_UPTIME_RAW`.
- `framesShown` = frames yielded; `framesDisplayed` = display marks (every one, also before the first pong); `framesSkipped` = gaps between consecutive yielded frame numbers (frames not shown, not damaged pictures); `keyRequests` = datagrams sent; `audioLost` = gaps in sound `seq`.
- `clockOffsetNs` = `hostNs - (sendNs + receiveNs) / 2` of the smallest-round-trip pong among the last 25 (`pongWindow`); a pong that echoes a time later than now is ignored.
- Delay = `arrival + clockOffsetNs - captureNs`, arrival = when the frame was assembled; `p95DelayMs` over the last 600 frames.
- Display delay = the mark's `at` (taken in the view right after the enqueue; same clock) `+ clockOffsetNs - captureNs`; `p95DisplayMs` over the last 600 marked frames, 0 when none.
- No arrival or display delay sample before the first pong (the offset is unknown until then; a device's clock is not the Mac's).
- `shownAt` is pruned to 2 s on every frame.
- Play numbers (`SessionStats`, all over sliding windows, no per-packet task): `bitrateMbps` = payload bytes of the frames completed in the last 2 s, as Mbit/s; `rttMs` = median of the last 23 ping / pong round trips (about 2.3 s; 0 before the first pong); the clock offset from the lowest round trip of the last 25 pongs (2.5 s); `p50DisplayMs` beside `p95DisplayMs` (same samples); `p95ArrivalGapMs`, `maxArrivalGapMs` = time between consecutive completed frames over the last 2 s (not across a video restart); `width`, `height` = the newest key frame's size (the session reads it from the frame header; the decoder is not asked).
- `sourceGaps` = completed frames whose `captureNs` is more than 1.5 frame periods (period = 1 / the session's `maxFps`; a game that runs slower than `maxFps` counts every frame) after the previous completed frame's: pictures the Mac never sent (the game hitched, or the Mac's rate cap refused one), as against network trouble; a total since the stream started (not compared across a video restart). `sourceFps` = frames by `captureNs` over the last 2 s (same span rule as `fps`), the Mac's own rate whatever the network did.
- `rateBps` (the rate the session asks for now; 0 when fixed), `rateCeilingBps` (the wish), `rateCuts` (`§ rate`).
- `host`: the newest `hostStats` datagram from the Host (once a second; nil before the first): `HostStats` (frames from the game, sent, dropped by its sender, resend datagrams, its video rate, the worst send lateness in us).
- Loss repair (`AssemblerCounts`, totals since the video stream started; a restart zeroes them): `nacksSent` (datagrams), `fragmentsAsked` (each index in each `nack`; a frame asked for whole counts 1, then the rest of its fragments once its count is known), `fragmentsRecovered` (asked-for fragments that arrived), `framesRepaired` (frames put out after a `nack`), `framesGivenUp`, `refreshes` (restarts at a repair frame), `restartsAsked` (`.refresh` events; `keyRequests` and `repairRequests` count the datagrams, retries included), `framesWaited` (frames dropped while a restart point was awaited), `fragmentsLate` (fragments of a frame given up within the last 200 ms: late, not lost).
- Over the session (`§ repair`): `repairRequests`, `escalations`, `keys` (key frames decoded after the first), `decodeErrors`, `acksSent`.
- `fps`, `bitrateMbps` = the last 2 s of frames / the time since the video stream (re)started (2 s at most, 0.5 s at least), so they are right from the first half second of every game.

#### pacing

`FramePacer<Frame>`, `PicturePacing` -> `FramePacer.swift` (pure: no clock, no UIKit); driven by `PictureUIView` (`Client/Sources/PictureView.swift`).

- `immediate`: the first `push` after a refresh returns the picture and the view shows it at once; a second before the next refresh is held (one slot) and `refresh()` returns it (it then counts as that interval's own picture, so a push after it is held again); a third replaces the held one (that one is late). Added delay: at most one refresh, only for the held picture. Why: two pictures in one interval otherwise gave a repeated picture and a skipped one (late + empty) whenever arrivals sat on the refresh boundary. Held pictures move to the store on a switch to `smooth`. `smooth` (default): `push` stores it; `refresh()` (called by a `CADisplayLink` tick, once per display refresh, capped at 60 a second) returns the oldest stored picture. `smooth` adds up to one refresh of delay (about 16.7 ms at 60 Hz) and so shows frames that arrive in bunches one per refresh instead of two in one.
- `smooth` drop rule, after the oldest is taken (`target` 1, `slack` 6 refreshes, `ceiling` = `target` + 2): more than `ceiling` stored -> drop the oldest down to `target` at once (a burst after a stall must not leave the picture several refreshes behind); else more than `target` stored -> count the refresh as "over", and after `slack` in a row drop down to `target` and count again; else reset the count. Why: with a few ms of jitter two pictures often land in one interval and none in the next, and the display clock drifts against the game's, so dropping at once threw away 8-15 pictures a second at a steady 60 (measured on a tablet); kept, the next refresh uses it. A source really faster than the display (61 per 60) still drops about one a second; delay is at most `ceiling` refreshes for a moment, `target` sustained.
- Counters, `takeCounts()` (reset on take; the view reports them once a second through `ClientModel.displayCounts`): `shown` = refreshes in which a new picture was shown (`immediate`: refreshes whose interval had a picture: pushed shown at once, or the held one taken at the interval's start); `late` = pictures that never got a refresh of their own (`immediate`: a held picture replaced by a newer one before its refresh; `smooth`: the dropped extras); `empty` = refreshes with nothing new.
- Looked like 30 fps although the Mac sends 60 (`immediate`, `late` and `empty` near 30: two pictures per refresh, then none): held pictures bring both to 0 for a 2 / 0 pattern; three in one interval still drop one.
- `mode` may change at any time (the view follows `settings.picturePacing`): switching to `immediate`, the next `push` drops every stored picture as late (they are older than the new one) and returns the new one; a refresh first shows the newest stored picture and drops the rest as late.
- Every enqueue, whichever path, is followed by `picturesShown` (the display mark).

#### recorder

`SessionRecorder` (actor), `SessionSample`, `SessionHeader`, `ArrivalMeter`, `SessionLogs` -> `PortalPlayer/SessionRecorder.swift`; driven by `ClientModel+Play.swift` (`startRecording`), fed by `PictureUIView`.

- Per session start (`startPlaying`): a new `Documents/sessions/<UTC yyyyMMdd-HHmmss>.log`; line 1 = header (`session v=1 app build platform os model display_max_hz title size fps_cap bitrate_cap_mbps smooth sound_buffer`: hardware model string, never the device's name; no Host name, address or pairing data), then one line a second. Off with `settings.recordSessions` (default on; Settings row "Keep session numbers on this device") or when the model has no `recordingsDirectory` (tests). No file-sharing plist keys: `scripts/client.sh logs` copies it (`build.md`).
- The file is created with the first line that has numbers (about 1 s in; a second without numbers writes nothing and the recording goes on; only the end of the play ends it), so the header carries what the view reported meanwhile. `display_max_hz` is the screen's maximum; if it is missing, trust the per-line `refresh_ms` (the rate in use).
- Housekeeping, at the start: only files named `yyyyMMdd-HHmmss[-n].log` (regular files) count; those beyond the newest 30 or beyond 20 MB in total go, oldest first (`SessionLogs.removals`). A failed write ends the recording of that session, `failures` counts it, nothing reaches the player. File work is on the recorder actor; the main actor only reads numbers once a second.
- Line, `key=value`, fixed order, numbers only (units in the key), unknown values left out: `t_s` · pacer, this window (view's report, about 1 s; left out when none in 2.5 s): `arrived shown late empty queue queue_target` · phase: `phase_mean_ms phase_min_ms phase_max_ms` (picture arrival minus the previous display refresh's time; drifting = the Mac's frame clock against the display), `refresh_ms` (the link's reported period), `gap_mean_ms gap_p95_ms gap_max_ms` (between arrivals) · `mac_fps source_gaps width height mbit delay_p50_ms delay_p95_ms decode_mean_ms decode_max_ms skipped` · `rate_mbps rate_ceiling_mbps rate_cuts rate_why` (word: last change's reason) · `rtt_floor_ms rtt_ms asked recovered given_up key_requests refreshes` (totals) · `sound_target_ms sound_level_ms underruns blocks_lost` · `host_from_game host_sent host_dropped host_resent host_rate_mbps host_late_us` (once `hostStats` came) · `thermal` (0...3) `low_power` (0/1). · appended last (older files lack them; a second without a sample leaves the key out): `net_gap_max_ms` (largest interval this second between two VIDEO datagrams, stamped in the session where each opens, before assembly, decode and the main queue; includes the session actor's own queueing, so a value above `gap_max_ms`'s network part with a normal `rtt_max_ms` points at the app) `rtt_max_ms` (largest ping / pong round trip this second; `rtt_ms` is a median). Both are read and reset by the recorder only (`ClientSession.takeSecondMaxima`; the panel's `stats()` does not touch them). Counters other than the pacer's are totals since the stream / session started. · appended after those (totals since the stream started, always present): `repair_requests` (`repair` requests sent) `escalations` (repair asks that became a key request) `keys` (key frames decoded after the first) `frames_repaired` (frames put out after a `nack`) `decode_errors` (frames the player could not decode); `refreshes` is the repair frames the session restarted at. Left out of the line (the stats hold them): `nacks_sent`, `restarts_asked`, `frames_waited`, `fragments_late`, `acks_sent`, the rate's start and low. `key_requests` = key frame requests sent (the frames themselves are not counted).
- Phase: `ArrivalMeter` in `PictureUIView`: `arrival` in `arrived` (main queue, `uptimeNs()`), `refresh` at the top of each display-link tick (`link.timestamp`, same clock; period = `targetTimestamp - timestamp`), `take()` with `displayCounts`. It reads times and touches neither the pacer nor the enqueue.

#### discovery

`FoundHost`, `HostBrowsing`, `HostBrowser` (`HostBrowser.swift`).

#### model

`ClientModel` (`@MainActor @Observable`) -> `ClientModel.swift` (screens, sessions, retry), `ClientModel+Play.swift` (pumps, stats, play calls); sentences in `Messages.swift`.

- One `ClientSession` at a time, with its tasks (`Link`); every action bumps `op`, and work that resumes under an older `op` is dropped (session closed, nothing shown).
- Sessions are LIBRARY (`open(host:resume: false)`: the Host resumes nothing, sends no media until the device plays) or RESUMING (`resume` absent: as before, a device that paused the game resumes it by being admitted). Library: `start()` / `openLastMac`, `choose`, `switchMac`, `pair`, `leave()`. Resuming only where play was interrupted and is picked up: the retry loop after a session lost while playing, `foreground()` after a background while playing, `reconnectApplying()` (each reopens with the lost session's `playChosen`, so a library session lost or backgrounded comes back as one). Rules: `portalkit.md § session-rules`.
- `playChosen` (observable): the session plays: opened resuming, or the Host CONFIRMED a game the person chose (`launch` / `resume` set `playAsked`; a `starting` / `running` state of that game confirms it, a state with a reason refuses it and the session stays a library one, its sentence shown; an `idle` answer, as to a `resume` of a game the Mac no longer has, ends the ask). Cleared at once by `leave()` and `goHome` (so `disconnect()`), so a background or a lost connection right after never reopens resuming. `macRows`' "playing" and the Continue card's "Playing" follow it (`LibraryText.continueState(_:preparing:playsHere:)`: "Starting", "Preparing", "Paused" otherwise). Screen rule, while a session is open: newest `gameState` `starting` / `running` -> `.playing` only when `playChosen`, else `.library` (the Continue card and the tile show the game live: "Paused", "Preparing 36 %"); `idle` / `paused` -> `.library`. `choose`, `pair`, `foreground` and a reconnect all end there. A fresh start with this device's game paused on the Mac shows the library with the Continue card, not play. An `idle` state ends the play: `playChosen` and the `launchAsked` / `playAsked` notes clear (a later background or lost connection reopens a library session; a stale note never relabels a crash); a failed launch / resume call clears them too.
- `games` is listed after every open and after every `gameState`; a reply asked earlier never overwrites one asked later. `refresh()` lists again (pull to refresh, the iPad's Refresh).
- `TitleID.isWellFormed` and `OptionLimits` now live in PortalKit (`Wire/OptionLimits.swift`, one definition with the Host reader); the wire decoder refuses an over-limit `options` before `OptionClean` sees it, and `ClientSession` ignores it (the session goes on) but yields one `optionRefusals` event: the model gives up the oldest unanswered options message like a refused one (wish back, the sentence, the call returns; a refused list says "could not load"), and every call also stops waiting after `optionReplyTimeout` (5 s). `full` in a reply says `OptionText.macFull`.
- Per-game options (`ClientModel+Options.swift`, `OptionRows.swift`, `OptionClean.swift`, `OptionText.swift`): `options(for:)`, `loadOptions`, `setOption`, `resetOptions`, session-scoped (dropped by `teardown()` and by `show()` of another Mac; a reply only counts for a title this session asked about, at most 32). Every reply is cleaned before it is kept (`OptionClean`: a variable must be `DM_` + `A-Z 0-9 _` (64 bytes), values plain and at most 128 bytes, labels cut at 80, notes at 240, no control / format / line-break characters, at most 200 rows and 64 choices, bad numbers, sizes and `needs` dropped, duplicates keep the first). #### look

The shared look (spec `§ Look`); every later screen draws with these four pieces and no colour literal.

- Tokens: `PortalPlayer/LookTokens.swift` (`RGBA`, `Contrast`, `LookPalette` dark / light, `Radii`, `Motion`); the palette also carries `onAccent`, `thickSurface`, `chip`, `scrim`, `accentGlow`, `shadow`, `sheen`, `halo`, `topLine`, `edgeIncreased` and the on-screen controller's `touch*` (idle white .14, pressed .45, outline .38, ring .06, label .6, pressed label black .7: the runtime's own look, a value test pins them; no contrast bar is applied: the on-screen controller is exempt, its look is the runtime's, ported not redesigned; labels read about 1.5:1 over a bright picture, `todo.md` Backlog). Client: `Theme.palette` (dark only in 1.0), `Theme.color(_:)`.
- Contrast rule (the on-screen controller is exempt: its look is the runtime's): text >= 4.5:1 on what is behind it; tested in `LookTokensTests` (Secondary / Tertiary / Accent text, Warning, Destructive on Background, glass, thick glass; `onAccent` on `accentFill` 4.78; the Continue tint for the 12 hue buckets). A new token pair adds its test.
- Icon decoding is bounded: data over 8 MiB or a side over 4096 (read from the header) is nil (both caps pinned to the exact value by `BoundedDecodeTests`); otherwise a thumbnail (64 px for the palette, at least 256 for the bitmap) is decoded, never the full image.
- `ArtPalette` (`from(pixels:)`, `from(png:)`, `tint`, `progressEnd`) and `AmbientImage` (`make`, `bitmapBlur`): pure, per icon; `-> look-glow`, `look-details`.
- Focus: `.buttonStyle(.portal(kind, radius:, fill:, text:))` on a `Button`, or `PortalFocusable(kind:…, action:) { content }` (a `Button` in that style: button trait, every default activation runs `action`); there is no free-standing modifier. `isFocused` is true only inside the focusable's own content, so the look is drawn there (`PortalFocusBody`); applying it from outside would silently do nothing. `forced:` pins a state (component sheet, not tvOS). Inside the content, `@Environment(\.portalFocused)` tells a value text to switch to the platter's colours; the style sets idle `fill` / `text`, an explicit `foregroundStyle` inside the label would override the platter's text. System focus effect off. Touch press = 0.96 scale. Verified on the Apple TV simulator: the first tile of the sheet takes the system's focus at launch and shows the look, nothing forced; moving focus by remote was not scripted (no press tool).
- `PortalTile(name:side:forced:dimmed:action:icon:)`: the icon is the button (scales, rings); the name sits outside it and never scales; `nameGap` 22 pt clears the ring's reach (ring + scale + shadow, about 18 pt). Later tile screens use it.
- `glass(_:radius:tint:)` (`GlassBackground.swift`): `glassEffect` on iOS / tvOS 26, else material + fill + edge; Reduce Transparency -> Grouped / thick surface; Increase Contrast -> stronger edge.
- `AmbientBackground(art:side:opacity:shade:blur:placement:)`: blur rendered once per icon at 128 px (cached by `ArtKey`: size + first / last 64 bytes, in `AmbientCache`, at most 64; a render that finishes after another icon took over is cached, never shown), drawn scaled; the bitmap's edges are clamped, so the view fades each edge with an eased (smoothstep) ramp over `blur x 2.5` pt, at least a quarter of the side, and a `.top` glow fades only at its bottom, so no screen height or width shows a line; no art = plain Background; hidden from VoiceOver.
- `LookSheet` (DEBUG): `-autoLookSheet` (+ `-autoLookPage 2` on a compact screen) shows every state. `scripts/client.sh run-sim [--sim "nxPortal <name>" | --tv] -autoLookSheet`. On tvOS a `Toggle` takes the system's own focus look.
